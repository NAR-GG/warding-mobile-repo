# screens/ — 화면 조립

`app/` 은 **라우팅과 전역 설정만** 둔다. 화면을 이루는 컴포넌트는 여기 온다.

```
app/                        라우트 (page.tsx · layout.tsx · globals.css)
screens/{화면}/             그 화면 전용 컴포넌트
packages/ui                 여러 화면이 쓰는 공용 컴포넌트
packages/api                서버 호출 + 도메인 타입
```

## 왜 `pages/` 가 아닌가

FSD 의 그 레이어가 맞지만, Next 에서 `pages/` 는 **레거시 라우터 디렉터리**라
그 이름을 쓰면 라우팅이 꼬인다. 그래서 `screens/` 로 둔다.

## 판별

- **`app/` 에 두는 것** — `page.tsx`·`layout.tsx`·`route.ts` 처럼 Next 가 경로로
  해석하는 파일과 전역 CSS. 그 외에는 두지 않는다.
- **`screens/` 에 두는 것** — 한 화면 전용 컴포넌트. 라우트가 얇아지고, 화면
  구성을 라우팅 경로(`[id]` 같은 폴더)에서 분리한다.
- **`packages/ui` 로 올리는 것** — 화면 2개 이상이 쓸 때. 미리 올리지 않는다
  (Flutter 의 "한 기능 전용 위젯은 `core/ui` 에 두지 않는다" 와 같은 규칙).

## `entities` 레이어를 두지 않는 이유

FSD 는 `entities/{도메인}/model` 에 도메인 타입을 두지만, 여기서는 **서버 응답을
아는 코드를 `packages/api` 한 곳**에 모은다. 타입(`types.ts`)과 변환
(`mappers.ts`)이 붙어 있어야 서버 형식이 바뀔 때 한 군데만 고친다. 분리하면
타입은 `entities`, 변환은 `api` 에 흩어져 같은 변경이 두 곳으로 번진다.

## `features` 레이어는 필요해질 때 만든다

좋아요·스크랩·투표처럼 **사용자 행동 + 그에 딸린 상태**가 생기면 그때
`features/{행동}/` 을 만든다. 지금은 읽기 전용 화면뿐이라 만들지 않는다 —
빈 폴더는 구조가 아니라 소음이다.
