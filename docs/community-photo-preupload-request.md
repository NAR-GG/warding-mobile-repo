# 커뮤니티 사진 선업로드 요청 — 등록 체감 딜레이 제거 (플러터)

작성일: 2026-08-30 · 대상: `warding-mobile-repo`

사진 포함 게시글 등록이 #227(병렬화·1600px 리사이즈) 이후에도 **1.5~2초** 걸린다.
남은 병목을 실측으로 분해했더니 전부 물리 거리라 코드로는 못 줄인다 — 대신
**업로드 시작 시점을 앞당기면 체감이 0 이 된다.**

**요청 한 줄**: 사진을 선택하는 순간 백그라운드 업로드를 시작하고, "등록" 버튼은
`createPost` 한 방만 남겨라.

---

## 남은 딜레이의 정체 (실측, 한국 기준)

| 구간 | 시간 | 줄일 수 있나 |
|---|---|---|
| Cloudinary 연결+TLS | ~440ms (connect RTT 220ms) | ❌ 업로드 엔드포인트가 원거리(미국) |
| 이미지 전송+응답 (~300KB) | +0.5~1s | ❌ 업링크 물리량 |
| 서명 발급 왕복 | ~150ms | ❌ (이미 병렬) |
| `createPost` 서버 처리 | ~20ms | 이미 빠름 |

앱 쪽 최적화(#227)와 서버 쪽 인덱스는 할 일을 다 했다. 남은 1.5~2초는
"등록 버튼을 누른 뒤에 업로드를 시작"하기 때문에 유저 눈앞에 그대로 보인다.

## 방법 — 선업로드 (업계 표준 패턴)

인스타그램(캡션 쓰는 동안 몰래 업로드), 트위터(`media/upload` 선행 → 트윗엔
media_id 만), 슬랙·디스코드(첨부 선택 즉시 업로드)가 전부 이 방식이다. 우리
구조(서명 → 직접 업로드 → `secure_url` 부착)는 트위터와 같은 모양이라 그대로 된다.

유저가 제목·본문을 쓰는 몇십 초 동안 업로드가 끝나 있으므로, 등록 버튼은
`createPost` 1왕복(~300ms)만 남는다.

## 구현 지침 (`post_write_viewmodel.dart`)

1. **사진 선택 즉시 업로드 시작.** `_photos` 에 추가하는 시점에 장별로
   `_images.upload(file)` Future 를 만들어 경로와 함께 들고 있는다
   (`Map<String, Future<String>>` 정도).
2. **삭제/교체 시 그 Future 결과만 버린다.** 업로드 취소까지는 불필요 —
   결과 URL 을 안 쓰면 그만이다(고아 파일은 아래 참고).
3. **등록 버튼**: 아직 안 끝난 업로드만 `Future.wait` 로 마저 기다린 뒤
   `createPost(imageUrls: ...)`. 이미 끝나 있으면 즉시 통과.
4. **실패 처리는 지금과 동일** — 한 장이라도 실패하면 전체 실패로 안내
   (사진 빠진 글이 올라가는 것보다 낫다는 기존 결정 유지). 선업로드 실패는
   등록 전에 미리 알 수 있으니, 해당 썸네일에 실패 표시 + 탭 재시도를 붙이면
   더 좋다(선택).
5. **업로드 중 등록 버튼은 막지 않는다** — 3번이 알아서 기다린다. 스피너
   문구만 "사진 올리는 중…"으로 구분해 주면 충분.

서버 변경: **0.** 서명은 글 등록 전에 받아도 무해하다 — URL 을 글에 붙이기
전엔 DB 에 아무것도 안 생긴다.

## 트레이드오프 — 고아 파일

선택만 하고 등록 안 하면 Cloudinary 에 파일이 남는다. 인스타도 그냥 버린다.
지금 규모에선 방치해도 되고, 거슬리면 백엔드가 나중에 "community/ 폴더에서
DB(`community_post_image`)에 없는 public_id 삭제" 배치를 붙인다(백엔드 몫,
요청 시 진행).

## 완료 기준

- 사진 3장 글 등록: 버튼 누른 뒤 완료까지 **0.5초 이내** (본문 작성에 10초 이상
  쓴 경우)
- 사진 선택 직후 바로 등록(업로드 미완): 기존과 동일하게 완료까지 대기 — 깨지지 않음
- 사진 삭제 후 등록: 삭제한 장의 URL 이 `imageUrls` 에 안 들어감
