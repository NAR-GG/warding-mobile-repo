# 커뮤니티 — 앱스토어·플레이스토어 심사 리스크

커뮤니티를 붙이는 순간 Warding 은 **UGC(이용자 생성 콘텐츠) 앱**이 된다. 지금까지는
읽기 전용 정보 앱이라 해당 없던 심사 조항이 통째로 적용된다.

이 문서는 **막힐 지점**과 **지금 앱에 없는 것**을 정리한다. 규칙 원문은
`docs/community-policy.md`, 백엔드 설계는 `nar-back-repo/docs/community-backend-design.md`.

---

## 요약 — 지금 상태로 내면 막힌다

| # | 항목 | 상태 | 심각도 |
|---|---|---|---|
| 1 | 이용약관(EULA)·개인정보처리방침 **앱 내 링크** | ⚠️ 코드 완료, **문서 미작성** | **리젝 확실** |
| 2 | 사진 권한 문구가 커뮤니티를 포함하지 않음 | ✅ 수정됨 | — |
| 3 | 연령등급 재설정 (App Store / Play 콘텐츠 등급) | ❌ 미반영 | **리젝 확실** |
| 4 | 개인정보 라벨 / Data safety 갱신 | ❌ 미반영 | **리젝 확실** |
| 5 | 신고 24시간 내 처리 체계 | ⚠️ 수단 없음 | **리젝 가능** |
| 6 | 신고·차단 기능 | ✅ 구현됨 | — |
| 7 | 계정 삭제 | ✅ 회원탈퇴 있음 | — |
| 8 | 문의 창구 | ✅ 구글폼 있음 | ⚠️ 위치 확인 필요 |

**아무것도 안 하고 제출하면 1·3·4 로 확실히 막힌다.** 셋 다 코드가 아니라 스토어
콘솔·문서 작업이라 개발자가 놓치기 쉬운 항목이다.

1번은 앱 쪽 코드가 붙었고 **약관 문서 작성과 리다이렉트 설정만 남았다.**

## 1. 이용약관·개인정보처리방침 — **결정 완료, 문서만 남음**

### 문제였던 것

앱 전체에 약관·개인정보처리방침 링크가 **한 군데도 없었다.** 소셜 로그인 버튼을
누르면 곧바로 가입·온보딩으로 넘어간다 — 동의 절차가 아예 없다.

법적으로는 즉시 위법은 아니다. 개인정보보호법 제15조 1항 4호가 **계약 이행에
필요한 최소 정보는 동의 없이 수집**할 수 있게 하고, 소셜 로그인으로 받는
닉네임·이메일이 여기 걸친다. 마케팅 푸시도 없어서(경기·솔랭 알림은 전부 서비스
알림) 정보통신망법 제50조 광고성 정보 동의도 해당 없다.

**문제는 Apple 이다.** Guideline 1.2 는 UGC 앱에 대해 *"이용자가 EULA 에 동의해야
하고, 그 약관에 불쾌한 콘텐츠와 악성 이용자에 대해 무관용임이 명시되어야 한다"*
고 요구한다. 법과 별개이고, 커뮤니티를 넣는 순간 새로 생기는 요건이다.

### 결정한 구조

**동의 방식 — 동의 간주 (체크박스 화면 아님)**

로그인 화면 하단에 한 줄.

```
로그인 시 이용약관 및 개인정보처리방침에 동의합니다
       ~~~~~~~~     ~~~~~~~~~~~~~~~~~~
```

"동의"라는 단어가 빠지면 동의 획득이 아니게 되므로 이보다 더 줄이지 않는다.

**국내 대형 앱은 체크박스 동의 화면이 더 흔하다.** `[전체 동의]` / `[필수]
이용약관` / `[필수] 개인정보처리방침` / `[선택] 마케팅 정보 수신` 형태다. 그럼에도
간주 방식을 택한 이유가 둘 있다.

**1. 체크박스가 필요한 진짜 이유는 선택 동의다.** 개인정보보호법은 필수 동의와
선택 동의를 구분해 받도록 하고, 선택 동의를 거부했다는 이유로 서비스를 거부할 수
없게 한다. 마케팅 수신 동의가 대표적인 선택 항목인데, 이걸 구분해 받으려면
체크박스 말고 방법이 없다. **거꾸로 말하면 선택 동의 항목이 없으면 체크박스를 둘
이유도 없다.** Warding 은 지금 마케팅 푸시가 없다 — 경기·솔랭 알림은 전부 서비스
알림이라 필수 범위다. 받을 게 필수 둘뿐이라 간주로 충분하다.

**2. 기존 회원 6,497명.** 명시적 동의로 가면 그들에게도 다음 실행 때 동의 화면을
띄워야 하고, 안 그러면 신규와 기존의 동의 상태가 갈린다.

> 체크박스가 필요해지는 시점은 명확하다 — **마케팅 푸시나 이벤트 알림을 보내기
> 시작할 때.** 그건 정보통신망법 제50조상 명시적 사전 동의가 필수다. 그때 만드는
> 동의 화면에 이용약관·개인정보처리방침도 같이 넣으면 된다.

**링크만 두면 안 된다.** Apple 이 보는 건 문서 제공이 아니라 동의라, "동의한
것으로 봅니다" 문장이 함께 있어야 한다.

**호스팅 — 내용은 노션, 주소는 우리 도메인**

```
앱 · 스토어 콘솔  →  https://nar.kr/terms     ─┐
                     https://nar.kr/privacy   ─┴→ (Cloudflare 리다이렉트) → 노션
```

노션 URL 을 앱에 직접 박으면 **노션 페이지를 옮기거나 재생성할 때 링크가 죽고,
고치려면 앱을 다시 심사받아야 한다.** 약관 링크가 죽은 채로 심사에 들어가면 그
자체가 리젝 사유다. 도메인을 앞에 두면 리다이렉트 대상만 갈아끼우면 된다 —
Cloudflare 가 이미 앞단에 있어서(`cloudflared`) Redirect Rule 한 줄이면 되고
백엔드 배포도 필요 없다.

나중에 자체 정적 페이지로 옮길 때도 앱 수정이 없다.

**표시 방식 — 외부 브라우저**

인앱 웹뷰가 대형 앱 관행이지만 `webview_flutter` 는 네이티브 의존성이라 넣는 순간
**Shorebird 코드푸시로 못 나가고 스토어 재제출이 필요**해진다. 약관을 읽히자고 낼
비용이 아니다.

커뮤니티 이용규칙을 앱 내 모달로 만든 건 성격이 다르다 — 글 쓰기 직전이 규칙을
읽을 유일한 순간이라 앱 밖으로 내보내면 아무도 안 본다.

### 약관 본문 구성 — 두 겹으로 나눈다

| 문서 | 담을 것 | 개정 |
|---|---|---|
| **이용약관** | 무관용 원칙 + 커뮤니티 이용규칙 준용 조항 + 제재 근거 | 사전 공지 필요, 드물게 |
| **개인정보처리방침** | 수집 항목(사용자 콘텐츠·사진 추가), 사업자 정보, 개인정보보호책임자 | 변경 시 고지 |
| **커뮤니티 이용규칙** | 세부 금지 행위 — `docs/community-policy.md` 에 초안 있음 | 공지 후 바로 |

약관에는 이 정도만 넣는다.

```
제N조 (금지행위 및 게시물 관리)
① 회사는 불쾌감을 주는 콘텐츠와 악성 이용자에 대해 무관용 원칙을 적용한다.
② 이용자는 별도로 정하는 「커뮤니티 이용규칙」을 준수하여야 한다.
③ 위반 시 게시물이 삭제되고 서비스 이용이 일정 기간 또는 영구적으로 제한될 수 있다.
```

**세부 조항을 약관 본문에 다 박으면 안 되는 이유** — 약관은 개정할 때마다 사전
공지가 붙는다(통상 적용일 7일 전, 이용자에게 불리한 변경은 30일 전). 규칙 한 줄
고치는 데 30일이 걸린다. 준용 구조면 규칙은 공지사항으로 알리고 바로 반영된다.

이게 백엔드 설계의 **D-6(규칙 전문을 서버에서 내리기)** 과도 맞물린다. 규칙이
약관과 분리돼 있어야 서버에서 갈아끼우는 게 의미가 있다.

### 코드 — 반영 완료

- `ApiConfig.webHost` = `https://nar.kr` — `host`(=`api.nar.kr`)는 API 서버라
  사람이 읽는 문서를 걸 자리가 아니라 따로 뒀다
- `ApiConfig.termsUrl` / `privacyUrl` (`nar.kr/terms`, `nar.kr/privacy`)
- 로그인 화면 하단 `LoginConsentNotice` — 문장 안에 링크 두 개, 각각 외부 브라우저
- 마이페이지 > 고객 지원에 `이용약관` / `개인정보처리방침` 항목

**남은 것은 문서 작성과 리다이렉트 설정뿐이다.** 이건 개발이 아니라 리드타임이
가장 긴 항목이라 커뮤니티 코드보다 먼저 시작하는 게 맞다.

## 2. 사진 권한 문구 — 커뮤니티를 포함하지 않음

`ios/Runner/Info.plist`:

```xml
<key>NSPhotoLibraryUsageDescription</key>
<string>프로필 사진을 변경하려면 사진 라이브러리 접근이 필요합니다.</string>
```

커뮤니티 글쓰기에서 같은 권한을 쓰는데 문구는 프로필만 말한다. **Apple 은 권한
문구와 실제 용도가 다르면 리젝한다**(Guideline 5.1.1 — 목적 문자열이 데이터
사용을 명확히 설명해야 함).

### 해야 할 것

문구를 둘 다 포괄하게 고친다.

```xml
<string>프로필 사진을 바꾸거나 커뮤니티 글에 사진을 첨부하려면 사진 라이브러리 접근이 필요합니다.</string>
```

Android 는 `image_picker` 가 Photo Picker 를 쓰면 별도 권한 선언이 없어 지금은
문제가 없다. `AndroidManifest.xml` 에 사진 권한이 선언되어 있지 않은 현재 상태가
오히려 안전하다 — **`READ_MEDIA_IMAGES` 를 추가하면 Play 에 권한 사용 사유를
따로 제출해야 하므로 추가하지 않는 게 낫다.**

## 3. 연령등급 — 반드시 올라간다

UGC 가 들어가면 등급 산정이 바뀐다.

- **App Store** — 연령등급 설문에 "제한 없는 웹 접근 / 이용자 생성 콘텐츠" 항목이
  있고, 체크하면 등급이 올라간다. 통상 **12+ 이상**, 필터링이 약하면 17+ 를
  요구받는다.
- **Play** — 콘텐츠 등급 설문을 **다시 제출**해야 한다. UGC 항목을 사실대로
  답하지 않으면 정책 위반으로 앱이 내려갈 수 있다.

### 왜 중요한가

**등급을 안 바꾸고 UGC 를 넣는 건 "허위 신고"로 취급된다.** 심사에서 걸리면 단순
리젝이 아니라 계정 경고로 이어질 수 있는 종류다.

### 해야 할 것

- 양쪽 콘솔에서 설문 재작성
- 등급이 올라가면 기존 사용자에게 미치는 영향 확인(가족 공유·스크린타임 제한 등)

## 4. 개인정보 라벨 / Data safety — 갱신 필요

커뮤니티는 **새로운 종류의 데이터를 수집**한다.

| 데이터 | 지금 | 커뮤니티 이후 |
|---|---|---|
| 사용자 콘텐츠(글·댓글) | 없음 | **수집·저장·공개** |
| 사진 | 프로필만 | **공개 게시물에 포함** |
| 식별자(닉네임)와 콘텐츠 연결 | 약함 | **강하게 연결됨** |

- **App Store** — App Privacy 에 `User Content` 항목 추가. "앱 기능" 용도, 사용자
  식별과 연결됨으로 표시.
- **Play** — Data safety 폼에 "사용자 생성 콘텐츠" 수집·공유 여부, 암호화 전송,
  삭제 요청 가능 여부를 다시 답한다. **삭제 요청 경로를 묻는데, 회원탈퇴가 있으니
  그걸로 답할 수 있다.**

라벨과 실제 동작이 다르면 리젝된다. 이건 코드 변경 없이 콘솔에서만 하는 일이라
잊기 쉽다.

## 5. 신고 24시간 내 처리 — 수단이 없다

Apple 1.2 는 **"신고된 불쾌한 콘텐츠를 24시간 내에 제거하고 해당 이용자를
차단해야 한다"** 고 명시한다.

지금 앱에는 신고 UI 가 있고 백엔드 설계에는 `community_report` 테이블과 3건 이상
Discord 알림이 있다. 하지만 **받은 신고를 실제로 처리할 화면이 없다.**

### 심사에서 어떻게 걸리나

Apple 리뷰어는 보통 이렇게 묻는다.

> 신고된 콘텐츠를 어떻게, 얼마 만에 처리하는지 설명하고, 그 절차를 보여달라.

"Discord 로 알림이 오고 사람이 DB 를 고칩니다"는 **답변으로는 통할 수 있지만**,
운영이 실제로 그렇게 굴러가는지가 관건이다. 리뷰 노트에 절차를 적어두면 통과
가능성이 올라간다.

### 선택지

| 선택지 | 심사 | 운영 |
|---|---|---|
| 백오피스 신고 큐를 먼저 만든다 | 가장 안전 | 출시가 밀린다 |
| Discord 알림 + 수동 처리, 리뷰 노트에 명시 | 통과 가능 | 사람이 붙어 있어야 한다 |
| 아무것도 없이 제출 | **리젝** | — |

**사진을 빼고 텍스트로 먼저 내면 이 리스크가 크게 줄어든다.** 불쾌한 텍스트는
지우면 끝이지만 이미지는 그렇지 않고, 리뷰어도 이미지가 있는 UGC 앱을 더 깐깐하게
본다.

## 6~8. 이미 있는 것

- **신고·차단** — 글·댓글 모두 `⋯` → 신고(사유 6종 + 기타 상세), 사용자 차단.
  Apple 1.2 와 Play UGC 정책의 핵심 요구를 형식적으로는 충족한다.
  **단, "차단"이 실제로 동작해야 한다** — 백엔드 `member_block` 이 붙기 전까지는
  UI 만 있는 상태다. 그 상태로 제출하면 리뷰어가 눌러보고 아무 일도 안 일어나는
  걸 발견한다.
- **계정 삭제** — 회원탈퇴가 마이페이지 > 계정에 있다. Apple 5.1.1(v) 충족.
- **문의 창구** — 마이페이지 > 고객 지원 > 고객센터(구글폼). Apple 이 요구하는
  "게시된 연락 수단"에 해당한다. 다만 **스토어 등록정보의 지원 URL 과 일치하는지**
  확인이 필요하다.

## 추가로 볼 것

### 한국 특수 사항

- **청소년보호책임자 지정·표시** — 정보통신망법상 일정 규모 이상의 사업자에게
  적용된다. 회원 6.5천 명이면 지금은 해당하지 않을 가능성이 높지만, 커뮤니티를
  운영하는 이상 확인해두는 게 맞다.
- 앱 자체는 국내 서비스라 별도 심사 영향은 없다.

### 리뷰 노트에 미리 적어둘 것

심사 제출 시 App Review 노트에 이걸 적으면 왕복이 줄어든다.

- 커뮤니티 이용규칙 위치(글쓰기 화면 하단 + 전체 보기)
- 신고 경로: 글·댓글 `⋯` → 신고 → 사유 선택
- 차단 경로: 같은 메뉴 → 이 사용자 차단
- 신고 처리 절차와 목표 시간(24시간 내)
- 테스트 계정 (비회원으로도 읽기가 되지만, 쓰기·신고·차단을 확인하려면 로그인
  계정이 필요하다)

### Play 는 UGC 를 어떻게 보나

Play 는 **"앱이 다루는 UGC 종류에 걸맞은 수준의 모더레이션"** 을 요구한다.
규모가 커지면 자동 모더레이션을 기대하지만, 지금 규모에서는 신고 기반 + 사람
검토로 충분하다. **"신고·차단 기능이 없거나 찾기 어려우면 재심사까지 리젝"** 이
명시되어 있으므로, **기능이 눈에 띄는 위치에 있어야 한다** — 지금처럼 `⋯` 메뉴
안에 있는 건 일반적인 패턴이라 문제없다.

## 순서 제안

**제출 전에 반드시 (코드 밖)**

1. 이용약관·개인정보처리방침 작성 → 노션 게시 → **`nar.kr/terms`·`nar.kr/privacy` 리다이렉트 설정**
   (앱 내 링크는 이미 붙었다)
2. 약관에 불쾌한 콘텐츠 무관용 + 커뮤니티 규칙 준용 조항 명시
3. App Store 연령등급 설문 / Play 콘텐츠 등급 설문 재제출
4. App Privacy / Data safety 에 사용자 콘텐츠·사진 반영

**제출 전에 (코드)**

5. 차단이 실제로 동작하도록 백엔드 `member_block` 연동 — **UI 만 있는 상태로
   제출하지 않는다**
6. 신고가 실제로 접수되도록 `community_report` 연동

> `NSPhotoLibraryUsageDescription` 문구 수정과 약관 링크는 이미 반영됐다.

**운영 준비**

8. 신고 처리 절차를 문서로 정해두고 리뷰 노트에 적는다
9. Discord 알림 채널을 실제로 보는 사람을 정한다
