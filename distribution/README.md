# distribution — 스토어 릴리스 노트

릴리즈마다 **여기 내용을 고친 뒤** 태그를 찍는다. 워크플로우가 이 파일들을 그대로
스토어에 올린다. 고치지 않으면 **지난 릴리즈의 노트가 그대로 나간다.**

```
distribution/
├── whatsnew/                     Google Play 용
│   ├── whatsnew-ko-KR            (500자 제한)
│   └── whatsnew-en-US
└── metadata/                     App Store 용
    ├── ko/
    │   ├── release_notes.txt     릴리즈마다 고친다 (4000자 제한)
    │   ├── description.txt       앱 설명 (4000자 제한)
    │   ├── keywords.txt          검색 키워드 (100자 제한, 쉼표 구분)
    │   ├── support_url.txt
    │   └── marketing_url.txt
    └── en-US/                    같은 구성
```

`release_notes.txt` 만 릴리즈마다 바뀐다. 나머지 넷은 앱 소개라 거의 고정이다.

## 양식

이전 릴리즈부터 쓰던 형태를 그대로 따른다. 스토어에 연속으로 보이는 글이라 릴리즈마다
모양이 달라지면 안 된다.

```
■ 아시안게임 순위표를 볼 수 있어요!
  - 홈 순위표에서 아시안게임을 고르면 A·B 그룹별 순위와 국가 국기가 보여요.
  - 아직 순위 데이터가 준비되지 않은 리그는 점선으로 표시돼 눌러도 열리지 않아요.

■ 새로 열린 리그 경기도 놓치지 않아요!
  - 아시안게임처럼 새 리그의 경기만 있는 날에도 경기 목록이 비지 않고 제대로 보여요.
```

- 묶음 제목은 `■` 로 시작하고 **느낌표로 끝낸다.** 기능 단위로 묶는다.
- 하위 항목은 두 칸 들여쓴 `- ` 로 쓰고, 그 변경이 사용자에게 무엇을 해 주는지 적는다.
- **"~해요" 체**로 쓴다.
- 여러 커밋이 한 기능이면 묶어서 결과만 쓴다. 색상값·PR 번호는 사용자에게 의미가 없다.

## AI 초안

릴리즈 빌드가 끝나면 워크플로우가 커밋 로그를 읽어 **이 양식으로 초안을 만들어 Discord 에
보낸다.** 초안은 자동으로 커밋되지 않는다 — 보고 판단해서 이 파일들에 반영한다.

사용자가 체감할 변경이 없는 릴리즈(CI·문서·리팩터링만 있는 경우)면 초안 대신 "체감할
변경이 없어 보인다"고 알린다. 없는 기능을 지어내지 않게 한 것이다.

### 초안을 고치고 싶을 때

Discord 알림의 **[✏️ 패치노트 수정]** 버튼을 누르면 입력창이 뜨고, 현재 초안이 미리
채워져 있다. 고쳐서 제출하면 **그 내용으로 심사에 올라간다** — 이 파일들을 직접 고치고
PR 을 머지할 필요가 없다.

고친 내용은 **iOS 심사와 Play production 양쪽에 반영된다.** 심사 제출 워크플로우가
패치노트를 함께 받아 올리기 때문이다.

다만 **Play 내부테스트에는 태그를 미는 시점의 파일 내용**이 올라간다. 그 단계는
테스터만 보므로 보통 문제가 없고, production 으로 승격할 때 고친 내용으로 덮인다.

## 왜 같은 내용을 두 벌 쓰나

스토어마다 요구하는 디렉터리 구조와 파일명이 다르다. Play 는
`whatsnew-<locale>`(확장자 없음), App Store 는 `<locale>/release_notes.txt` 다.
로케일 표기도 다르다 — Play 는 `ko-KR`, App Store 는 `ko`.

내용이 같아도 되므로, 한쪽을 쓰고 복사하면 된다.

```bash
cp distribution/whatsnew/whatsnew-ko-KR distribution/metadata/ko/release_notes.txt
cp distribution/whatsnew/whatsnew-en-US distribution/metadata/en-US/release_notes.txt
```

## 어디에 쓰이나

| 파일 | 쓰는 곳 | 시점 |
|---|---|---|
| `whatsnew/*` | `release-deploy.yml` → Play 내부테스트 업로드 | 태그 push |
| `metadata/*/release_notes.txt` | `submit-for-review.yml` → App Store 심사 제출 | 버튼 실행 |
| `metadata/*/description·keywords·*_url` | 같은 워크플로우가 함께 올린다 | 버튼 실행 |

Play 는 업로드할 때 노트가 붙고, production 승격 때는 그 노트가 그대로 따라간다.
App Store 는 심사 제출 시점에 "새로운 기능" 칸으로 들어간다.

## 업데이트 팝업 (필수 업데이트)

앱은 스토어에 새 버전이 있어도 **팝업을 띄우지 않는다.** 일반 배포는 스토어 자동
업데이트로 조용히 받게 둔다. 꼭 올려야 하는 릴리즈(서버 API 호환이 깨지는 경우,
치명적인 버그 수정 등)만 앱 설명 맨 끝에 최소 버전 태그를 단다.

```
[:mav: 1.0.43]
```

설치된 앱의 버전이 이보다 낮으면 앱을 켤 때마다 팝업이 뜬다. 버전은 pubspec 의
`+` 앞부분(빌드 번호 제외)과 비교한다.

- **App Store**: `metadata/ko/description.txt` 와 `metadata/en-US/description.txt`
  끝에 태그를 단다. 심사 제출 때 함께 올라가고, **그 버전이 출시돼야** 효력이 난다.
- **Google Play**: 설명은 이 레포가 관리하지 않는다. Play Console → 기본 스토어
  등록정보 → 자세한 설명 끝에 같은 태그를 단다. 등록정보 검토를 거친다.
- 태그는 **이미 스토어에 나간 버전 이하**로 적는다. 앱이 스토어에 더 높은 버전이
  있는지도 함께 확인해서, 잘못 적으면 팝업이 아예 뜨지 않는다.
- 필수 업데이트가 끝나도 태그는 그대로 둬도 된다. 그 버전 이상인 사용자에게는
  아무 영향이 없다.
- 이 동작은 이 변경이 들어간 다음 릴리즈(1.0.43 예정)부터다. 그 이전 버전 설치자는 옛 로직이라, 스토어에 새 버전이
  있으면 계속 매번 팝업을 본다.

## 주의

- **Play 500자 제한**은 워크플로우가 업로드 전에 검사해 넘으면 실패시킨다.
- **App Store 설명·키워드도 이제 여기서 관리한다**(2026-10-16부터). 그래서
  **App Store Connect 에서 고친 설명·키워드는 다음 제출 때 이 파일 내용으로 덮어써진다.**
  ASC 에서 직접 손보지 말고 여기를 고쳐 PR 로 올린다.

  원래는 `release_notes.txt` 만 두고 나머지는 ASC 에 있는 값을 믿었다. 그 전제가
  1.0.34+84 에서 깨졌다 — ASC 에 새 버전이 생기면 설명·키워드·지원 URL 이 빈 채로
  만들어지고(이전 버전에서 복사되지 않는다), `deliver` 는 파일이 없는 필드를 건드리지
  않으니 빈 값 그대로 심사에 올라가 Apple 이 거부한다.

      appStoreVersions ... is not in valid state.
        You must provide a value for the attribute 'description'

  사람이 ASC 에서 매번 채우는 것과 파일로 두는 것 중 후자를 골랐다. 자동 제출 경로가
  사람 손을 타지 않고 끝나는 게 애초에 이 자동화의 목적이다.
- **언어 폴더마다 다 있어야 한다.** `ko` 만 채우고 `en-US` 를 비우면 영어 쪽에서 같은
  거부가 난다. Apple 은 등록된 모든 언어에 대해 요구한다.
- 사용자에게 보이는 글이다. 내부 용어(`BottomActionBar`, 커밋 해시 등)를 쓰지 않는다.
