# Intent: 릴리즈 빌드·배포 자동화

## Problem

릴리즈가 전부 로컬 수동이다. `shorebird release ios` / `shorebird release android` 를
직접 돌리고, 나온 ipa 를 Transporter 로, aab 를 Play Console 로 손수 올리고, 태그도
빌드 직전에 손으로 찍는다. 테스트 CI(`ci-flutter-test.yml`)와 릴리즈 직전 e2e
(`e2e-release-check.yml`)는 있지만 **빌드·배포 쪽은 자동화가 하나도 없다.**

사람이 매번 올바른 절차를 기억해야 하는 구조라 이미 사고가 두 번 났다.

- **1.0.3 iOS**: `shorebird release` 가 아닌 `flutter build ipa` 로 빌드해 스토어에
  올렸다. Shorebird 업데이터가 안 들어가서 그 빌드를 설치한 사용자는 다음 스토어
  릴리즈가 나갈 때까지 코드 푸시 패치를 받지 못했다.
- **1.0.14+21**: gitignore 된 `ios/Flutter/Secrets.xcconfig` 가 빠진 워크트리에서
  빌드해 네이버 Client Secret 이 빈 값으로 들어갔다. 네이버 로그인만 조용히 실패했다.

두 사고 모두 "빌드 환경이 사람 손에 달려 있다"는 같은 원인이다. 지금은
`Secrets.xcconfig` 가 비면 Release 빌드를 실패시키는 가드가 들어가 있지만, 그건 한
사례를 막은 것이지 구조를 바꾼 것은 아니다.

릴리즈 직전 e2e 를 돌리는 규칙도 사람의 기억에 의존한다. 실제로 1.0.33+79 를 뽑을 때
직전 e2e 가 4커밋 전에 돈 것이었고, 그 사이에 UI 변경이 들어와 있었다.

## Proposed outcome

`release/<version>` 태그를 밀면 검증·e2e·빌드·스토어 업로드가 자동으로 이어지고,
**사람은 "이 커밋을 릴리즈한다"와 "심사에 올린다" 두 가지 결정만** 한다.

- 올바른 빌드 명령(`shorebird release`)이 워크플로우에 박혀 있어 다른 명령을 고를 수 없다.
- gitignore 된 시크릿 파일을 CI 가 Secrets 에서 복원하므로 "내 머신에만 있는 파일"
  때문에 깨진 빌드가 나가지 않는다.
- e2e 통과가 빌드의 선행 조건이라 건너뛸 수 없다.
- 태그와 `pubspec.yaml` 의 버전이 다르면 빌드 전에 멈춘다.
- shorebird 릴리즈와 커밋의 대응이 태그로 남아 "이 릴리즈가 어느 코드였나"를
  역추적할 수 있다.

## Affected users and systems

- **개발자(배포하는 사람)**: Transporter 드래그와 Play Console 업로드가 사라진다.
  대신 Secrets 관리와 인증서 갱신이라는 새 운영 부담이 생긴다.
- **앱 사용자**: 직접 보이는 변화는 없다. 다만 위 두 사고 같은 배포 실수가 줄어든다.
- **GitHub Actions**: macOS 러너를 릴리즈마다 쓴다(e2e + iOS 빌드). ubuntu 보다 느리고
  비싸다.
- **Apple / Google 콘솔**: CI 가 쓸 API 키·인증서·서비스 계정이 새로 필요하다. 이것들은
  만료·회수 관리 대상이 된다.
- **`e2e-release-check.yml`**: 릴리즈 파이프라인이 호출할 수 있어야 하므로 트리거가
  늘어난다. 기존 수동 실행 경로는 유지해야 한다.

## Constraints

- **빌드는 반드시 `shorebird release` 여야 한다.** `flutter build ipa`/`appbundle` 은
  금지다(1.0.3 사고). 이건 타협 대상이 아니다.
- **패치는 릴리즈 버전과 정확히 일치해야 한다.** 그래서 버전의 단일 출처는
  `pubspec.yaml` 이어야 하고, CI 가 빌드 번호를 제멋대로 만들어내면 안 된다.
- **스토어 업로드·심사 제출은 되돌리기 어렵다.** 자동화 범위를 정할 때 "실수로 나갔을
  때 되돌릴 수 있는가"가 기준이 되어야 한다.
- 개발자가 한 명이라 인증서 공유를 위한 별도 저장소를 유지하는 비용이 이득보다 크다.
- 네이티브 의존성·에셋 변경은 코드 푸시로 못 나가고 스토어 재제출이 필요하다. 자동화가
  이 구분을 흐리면 안 된다.

## Open questions

- 심사 제출까지 자동화해야 하는가? 손은 덜 가지만 되돌리기가 어렵고, 이미 심사 중인
  빌드가 있으면 제출이 거부되는 등 CI 가 처리하기 어려운 상태가 있다.
  → **해결됨**: 자동화하지 않는다. 조사 결과 Apple 공식 레퍼런스 워크플로우와 Shorebird
  공식 가이드가 모두 TestFlight 에서 멈추고, `deliver submit_build` 에 CI 가 재시도로
  넘을 수 없는 블로커가 있다. 대신 **버튼으로 실행하는 별도 워크플로우**로 뺀다.
  자세한 근거는 [spec.md](./spec.md) 의 Decisions 참고.
- Play production 승격과 단계적 출시를 자동화할 것인가?
  → **해결됨**: 내부테스트까지만 올린다. 승격은 콘솔에서 사람이 한다.
- 구버전 릴리즈에 패치를 낼 때 릴리즈별 브랜치가 필요한가? 지금은 태그에서 worktree 를
  따서 처리하는데, 이 방식이 자동화와 어떻게 맞물릴지 정하지 않았다.
- 릴리즈 실패 시 다른 워크플로우처럼 문서 초안 자동 생성(에스컬레이션)을 붙일 것인가?
  릴리즈 실패는 대부분 서명·자격 문제라 문서보다 알림이 적합해 보인다.
