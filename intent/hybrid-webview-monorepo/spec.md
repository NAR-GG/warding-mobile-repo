# Spec: 웹뷰 점진 전환 — 모노레포 배치와 토큰 단일 출처

Intent: [intent.md](./intent.md)
warding-docs: 해당 없음 (개발 쪽 구조 작업)

## Summary

Flutter 앱을 유지한 채 컨텐츠성 화면을 웹뷰로 점진 전환한다. 이를 위해 세 가지를 정한다.

1. **토큰 단일 출처** — JSON 소스 하나에서 Dart와 CSS를 생성하고, 생성물 일치를 CI로 검증한다.
2. **브리지 규약** — 웹↔네이티브 통신을 단계(Stage)로 쪼개 누적 호환으로 넓힌다.
3. **레포 배치** — `apps/` + `packages/` 표준 모노레포로 간다.

3번이 이 Spec의 핵심 결정이다. **처음에는 Flutter를 루트에 두는 비대칭 배치로 결정했다가,
2026-11-17에 `apps/mobile/`로 내리는 쪽으로 뒤집었다.**

원래 근거는 "릴리즈·패치 자동화가 레포 루트를 Flutter 루트로 가정하고, 그 가정은 태그를
밀어야 검증된다"였다. 실제로 세어 보니 경로 참조는 워크플로우 6개에 36곳이었고, 그중
cwd를 바꿔야 하는 것은 13곳이었다. 기계적 치환으로 끝나는 분량이고, **태그를 밀지 않고도
검증되는 경로가 대부분이었다** — `flutter analyze`·`flutter test`·`flutter build ios`,
그리고 셸 회귀 테스트(`patch-deploy-test.sh`)가 패치 가드 정규식을 직접 검증한다. 실제로
그 테스트가 치환 오탐 1건을 잡아냈다(`ios/Runner/Info.plist`가 접두어 없이 남았다).

검증되지 않는 범위는 **`shorebird release`·`shorebird patch` 실행과 스토어 업로드**뿐이다.
이건 태그를 밀어야 돈다. 남은 위험으로 받아들이고, 다음 릴리즈를 **빌드 번호를 올려
한 번 더 밀 수 있는 여유가 있을 때** 하는 것으로 둔다.

바꾼 이유는 비대칭 배치가 앱이 둘인데 한쪽만 특별 대우하는 구조여서다. 웹이 커질수록
"Flutter만 루트"라는 예외를 계속 설명해야 한다.

## Requirements

### 기능

- 토큰 소스 JSON에서 `core/theme/app_colors.dart`(또는 후속 토큰 파일)와 웹용 CSS를 생성한다.
- 생성은 결정적이다. 같은 소스에서 항상 같은 바이트가 나온다.
- 생성물이 소스와 어긋나면 CI가 실패한다.
- 토큰에 색·간격·모서리·그림자·모션·컴포넌트 토큰을 담는다.
- 웹뷰 페이지가 `scale` 수식을 CSS로 재현해 네이티브와 같은 치수로 렌더된다.
- 웹 페이지가 웹뷰 안인지 일반 브라우저인지 감지하고, 브라우저에서는 네이티브 의존 기능을
  비활성화한다.
- 웹↔네이티브 통신이 단방향 → 브로드캐스트 → 양방향 호출 순으로 확장되며, 뒤 단계가 앞
  단계를 깨지 않는다.

### 비기능

- ~~릴리즈·패치 워크플로우의 경로 가정을 변경하지 않는다.~~ → **변경했다.** 대신
  `apps/mobile/` 접두어 치환 + `working-directory` 13곳으로 끝내고, 셸 회귀 테스트가
  패치 가드 정규식을 검증한다.
- 웹 디렉터리 추가가 Flutter 빌드·analyze·test에 영향을 주지 않는다.
- 토큰 생성이 Flutter 빌드의 선행 조건이 되지 않는다 (생성물을 커밋하므로).
- 네이티브↔웹뷰 이음새에서 배경 플래시가 보이지 않는다.

## Design / Approach

### 레포 배치

```
warding-mobile-repo/
  apps/
    mobile/                     ← Flutter (2026-11-17에 루트에서 내렸다)
      pubspec.yaml
      lib/core/theme/
        app_colors.dart         ← 생성물 (커밋됨, 수정 금지 헤더)
    web/                        ← 웹뷰용 Next.js 앱
  packages/
    design-tokens/              ← 토큰 단일 출처
      source/
        common.json             간격·모서리·그림자·모션·타이포
        theme.json              색·컴포넌트 토큰
      build/
        tokens.css              웹 소비용
        app_colors.dart         turbo 캐시 앵커 (아래 참고)
      build.mjs                 생성기 + 커스텀 Dart 포맷터
      sync-dart.mjs             생성된 Dart → apps/mobile 복사
  tools/discord-bridge/         npm 으로 독립 운영 (워크스페이스 밖)
  turbo.json                    태스크 러너
  pnpm-workspace.yaml           apps/* + packages/*
```

**토큰 PR 하나로 Dart 생성물과 CSS 생성물이 같이 바뀌므로, 드리프트가 구조적으로
막힌다.** 이것이 모노레포에서 실제로 얻는 이득이다.

웹을 별도 레포로 두는 안도 검토했다. 토큰만 패키지로 공유하면 되지만, 그러면 토큰 변경이
두 레포에 걸친 PR 두 개가 되고 버전 어긋남이 생긴다. 지금 막으려는 문제가 그것이므로
같은 레포를 택한다.

#### `packages/` 에 design-tokens 하나만 두는 이유

표준 모노레포 예시에는 `shared-types`·`shared-api`·`ui-components` 가 흔히 나온다.
후보 4개를 실측으로 평가했고, **전부 "한쪽만 존재"라 공유할 대상이 없었다.**

| 후보 | 실측 | 판단 |
|---|---|---|
| `shared-types` | Flutter 가 코드생성을 안 쓴다 (`pubspec.yaml` 에 openapi·json_serializable·freezed 전부 없음) | 스키마 254개를 Dart 로 뽑는 경로가 없다. 만들면 TS 전용 타입 모음이 되고, 그건 `apps/web/` 안에 둘 것이다 |
| `shared-api` | `apps/web` 의 API 호출 0건 | **2026-11-17에 `packages/api` 로 만들었다** — Flutter 와 *공유*하는 게 아니라 **웹 전용** 클라이언트다. 아래 참고 |
| `ui-components` | Flutter 위젯 47 vs Next 컴포넌트 2 | **2026-11-17에 `packages/ui` 로 만들었다** — 아래 "웹 중심 전환" 참고. Dart 와 React 가 코드를 공유하는 것이 아니라, 화면이 웹으로 옮겨가면서 **React 쪽이 단일 구현이 되는** 방향이다 |
| 브리지 메시지 타입 | 웹에 Stage A 있음, Flutter 쪽 `WardingBridge` 참조 0건 | 가장 유망하지만 양쪽 구현이 생긴 뒤다. 그리고 Dart 가 선언을 읽으려면 다시 코드생성이 필요하므로, **Stage 표에 적고 양쪽에 손으로 쓰는 쪽이 싸다** |

**타입·API 공유가 불가한 공통 원인은 Flutter 가 코드생성을 쓰지 않는다는 것이다.**
"선언 하나를 두 언어가 읽는" 형태는 토큰(JSON → Dart·CSS 생성)에서만 성립한다.

#### 웹 중심 전환과 `packages/ui`

**전환 범위를 "컨텐츠성 화면만" 에서 "목록·상세·폼까지 웹, Flutter 는 셸만" 으로
넓혔다.** 그러면 UI 공유의 성격이 바뀐다 — Dart 와 React 가 같은 코드를 쓰는 것이
아니라, **화면이 옮겨가는 만큼 React 쪽이 유일한 구현이 된다.** 그래서
`ui-components` 를 "불가"에서 `packages/ui` 로 뒤집었다.

받아들인 것: 오프라인 동작과 네이티브 수준의 즉각적 화면 전환을 포기한다. 얻는 것:
레이아웃 변경에 스토어 심사가 필요 없다 — Shorebird 패치가 과금 때문에 막힌 지금
그 자리를 메우는 유일한 수단이다.

`packages/ui` 는 **빌드하지 않는다.** 소스(`.tsx`)를 그대로 내보내고 Next 가
`transpilePackages` 로 컴파일한다. 패키지마다 번들러를 두면 토큰 → UI → 웹으로 단계가
늘고 중간 산출물을 또 캐시 앵커로 관리해야 한다(토큰 쪽에서 겪은 문제다).

**첫 3개 컴포넌트(`BoardBadge`·`Button`·`DetailHeader`)는 Dart 위젯에서 수치를 그대로
옮겼고, 실제 렌더로 값을 대조했다**(375 뷰포트에서 버튼 34×110.5·radius 8·14px, 배지
padding 2/6·radius 4·11px, 헤더 34 + padding 18.5/20/22·18px — 전부 Dart 명세와 일치).

**겪은 함정 3개. 전부 빌드는 통과하고 실행해야 드러난다.**

| 함정 | 증상 | 규칙 |
|---|---|---|
| `calc(34px * var(--scale))` | 그 선언이 통째로 무효. 콘솔도 조용하다 | `--scale` 자체가 px 단위(`clamp(...)/375`)다. **단위 없이** `calc(34 * var(--scale))` |
| 서버 컴포넌트가 `onClick` 전달 | 런타임 500 `Event handlers cannot be passed to Client Component props` | 클라이언트 경계는 **호출부**에 둔다. 라이브러리에 `'use client'` 를 붙여도 안 풀린다 |
| 전역 `* { padding: 0 }` | 버튼 높이·여백이 무너진다 | `@import` 는 CSS 규격상 맨 앞으로 끌어올려져 **순서로 못 이긴다**. 리셋을 좁힌다(폼 요소 제외) |

구독 버튼은 폭을 고정하지 않는다 — Dart 가 `TextPainter` 로 '구독'/'구독중' 을 재서 더 긴
쪽에 맞추는 것과 같은 목적으로, CSS 는 더 긴 라벨을 `::before` 로 숨겨 깔아 폭을 잡고
실제 라벨을 그 위에 겹친다. 로케일이 늘어도 CSS 를 고치지 않는다.

#### `packages/api` — 웹 전용 클라이언트

**Flutter 와 타입을 공유하지 않는다.** 코드생성이 없어 Dart 쪽을 생성할 수 없다.
대신 **Dart 모델의 널 판단을 복제한다** — 같은 응답에서 두 플랫폼이 다른 화면을
그리면 안 되기 때문이다.

- `Result<T>` 를 돌려준다(`{ok:true,value} | {ok:false,failure}`). Flutter 의
  `Either<Failure, T>` 와 같은 계약이고, `Failure` 분류도 같다
  (`server`·`network`·`parse`·`unauthorized`·`noData`). 401·403 을 따로 가르는
  이유도 Dart 와 같다 — "다시 로그인" 과 "잠시 후 다시" 는 다른 안내다.
- 타임아웃 15초. Flutter `kDefaultApiTimeout` 과 같은 값이다.
- 토큰을 스스로 갖지 않는다. 호출부가 `options.token` 으로 넘긴다.

**OpenAPI 스펙의 `required` 를 그대로 믿지 않는다.** 커뮤니티 글 상세는 스펙상
required 가 0개라 전부 optional 로 읽히지만, 실제 응답은 대부분 값이 온다. Dart
모델이 실전 기준으로 정해 둔 널 여부를 따른다.

**그 판단이 틀린 것을 실측으로 잡았다.** `viewer` 를 "비회원이면 null" 로 설계했는데,
비회원 조회에서도 서버는 `viewer` 를 객체로 내려준다(전부 false). Dart 도
`CommunityPostViewer._empty` 로 메워 non-null 로 노출하고 있었다. **타입 체크는
런타임 응답을 보지 않으므로** 매퍼 회귀 테스트를 붙였고 PR마다 돈다.

**첫 전환 화면(커뮤니티 글 상세)을 SSR 로 띄워 설계를 검증했다.**

| 확인한 것 | 결과 |
|---|---|
| 비회원 조회가 열려 있나 | ✅ HTTP 200 (SSR 의 전제) |
| 서버가 보낸 HTML 에 실데이터가 있나 | ✅ 제목·작성자·조회수·좋아요 전부 포함 |
| 스펙 ↔ 실제 응답 | ✅ 필드 누락·추가 0건 |
| 라우트 모드 | ✅ `ƒ /community/post/[id]` (SSR) |

**본문은 `body` 블록만 그린다.** `images` 배열에 같은 이미지가 또 오는데 둘 다
그리면 사진이 두 번 나온다(실측). Flutter `post_block_renderer.dart` 도 블록만 쓴다.
블록 타입은 text·image·link·embed 4개고, 모르는 타입은 건너뛴다 — 서버가 타입을
추가해도 화면이 안 깨진다.

**없는 글은 404 이고 "삭제되었거나 없는 글" 로 안내한다.** `noData` 와 묶는 이유는
재시도해도 소용없다는 점이 같아서다. 네트워크 실패만 "다시 시도" 를 권한다.

#### 웹 내부 구조 — FSD 를 얕게

프론트에서 흔한 선택지는 Atomic Design · DDD · FSD 셋인데, 앞의 둘은 이 레포에
맞지 않는다.

| 후보 | 판단 |
|---|---|
| Atomic Design | **안 쓴다.** atoms/molecules/organisms 의 경계가 주관적이라 분류에 시간이 든다. 디자인 시스템이 풀려는 문제는 이미 `packages/design-tokens` 가 값 단일 출처로 해결했다 |
| DDD(레이어드) | **과하다.** entity·aggregate·도메인 서비스는 비즈니스 규칙이 클라이언트에 있을 때 값이 있다. 여기 규칙은 전부 서버에 있고 웹은 받아서 그린다 |
| FSD | **얕게 쓴다.** 의존 방향이 한 방향이고 Flutter 쪽 규칙(`app → features → core`)과 같은 사고 모델이라 두 플랫폼을 같은 머리로 읽는다 |

구조는 [FSD 공식 Next.js 가이드](https://feature-sliced.design/docs/guides/tech/with-nextjs)를
그대로 따른다.

```
apps/web/
├── app/                  Next 라우트. 화면을 re-export 만 한다
└── src/
    ├── _pages/{화면}/
    │   ├── index.ts      공개 API
    │   └── ui/           화면 컴포넌트
    └── shared/           웹 전용 공용 코드 (브리지 등)
packages/ui               여러 화면이 쓰는 공용 컴포넌트   (FSD 의 shared/ui)
packages/api              서버 호출 + 도메인 타입 + 매퍼   (FSD 의 shared/api)
```

**레이어를 다 만들지 않는다.** FSD 는 7개 레이어를 정의하지만 화면이 하나뿐인
지금 전부 만들면 빈 폴더가 구조가 아니라 소음이 된다.

- **`_pages` 의 밑줄은 공식 권장이다.** Next 가 `app/`·`pages/` 를 라우터
  디렉터리로 쓰므로 FSD 레이어 이름과 충돌한다. 공식이 `_app`·`_pages` 접두사를
  안내하고 공식 린터도 인식한다. 회피책 3개를 실측했고 **전부 빌드가 깨진다**:

  | 시도 | 결과 |
  |---|---|
  | 루트에 `pages/` | Next 가 라우트로 인식 → `pages/x/index.ts` 를 `/x` 로 보고 "default export 없음" |
  | 라우트를 `src/app` 으로 이동 | Next 15 가 타입 검증기 상대경로를 잘못 생성 |
  | `pageExtensions` 로 좁히기 | App Router 라우트가 전부 소멸, 404 만 남는다 |

  `app/` 을 **루트에 남기고** FSD 레이어만 `src/` 로 내리면 셋 다 피한다.
- **라우트는 re-export 한 줄이다** —
  `export { CommunityPostPage as default } from '@/_pages/community-post';`
  조립을 라우트에 두면 `app/` 이 다시 두꺼워진다.
- **`entities` 를 두지 않는다.** FSD 는 `entities/{도메인}/model` 에 도메인
  타입을 두지만, 여기서는 **서버 응답을 아는 코드를 `packages/api` 한 곳**에
  모은다. 타입과 매퍼가 붙어 있어야 서버 형식이 바뀔 때 한 군데만 고친다 —
  나누면 같은 변경이 두 곳으로 번진다.
- **`features` 는 좋아요·스크랩·투표를 붙일 때 만든다.** 지금은 읽기 전용이다.

**웹뷰라서 특별히 지켜야 하는 것은 라우팅이다.** 네이티브 스택과 Next 라우터가
따로 돌기 때문에, **웹의 화면 단위가 네이티브가 아는 화면 목록과 1:1이어야**
한다. 웹 안에서 자유롭게 라우팅하면 뒤로가기가 어긋난다. 그 목록의 단일 출처가
`app/navigation/webview_routes.dart` 다(위 "Flutter 쪽 배치" 참고).

`tools/discord-bridge` 도 패키지로 옮기지 않는다 — npm + Vercel 배포로 독립 운영 중이라
pnpm 워크스페이스에 묶으면 lock 충돌과 배포 경로 변경이 따라온다.

#### 태스크 러너: turbo, 그리고 캐시 함정

`pnpm build` 가 토큰 → 웹 순서를 보장한다. `apps/web` 이 `warding-design-tokens` 를
`workspace:*` 로 의존 선언해서 그래프가 잡힌다. Flutter 는 turbo 그래프 밖이다(Dart 를
모른다).

**turbo 의 `outputs` 는 패키지 밖을 캐시하지 못한다.** 생성기가
`apps/mobile/lib/core/theme/app_colors.dart` 를 직접 쓰게 두면, 캐시 적중 시 그 파일이
복원되지 않는데 turbo 는 `FULL TURBO` 로 성공을 보고한다 — 실측으로 재현했다. 생성물이
사라진 채 "성공"이 찍히고 그 뒤 `flutter analyze` 가 터진다.

그래서 **생성과 복사를 분리했다.**

| 태스크 | 하는 일 | 캐시 |
|---|---|---|
| `build` | `packages/design-tokens/build/` 에 CSS·Dart 생성 | 캐시된다 |
| `sync:dart` | `build/app_colors.dart` → `apps/mobile/` 복사 | `cache: false` (매번 돈다) |

`build/app_colors.dart` 를 커밋하는 이유가 이것이다 — 캐시 앵커다. 이 함정은 눈에
보이지 않으므로 `.github/workflows/turbo-cache-test.sh` 가 PR마다 3가지를 검증한다:
캐시 적중 상태에서 Dart 가 복원되는지, `build` 가 실제로 캐시되는지, 소스 변경이 Dart 까지
반영되는지.

**Nx 는 지금 넣지 않는다.** Nx 가 turbo 를 이기는 지점(프로젝트 그래프 기반 affected,
플러그인 추론)은 JS/TS import 그래프에서 나오는데, 여기 JS 패키지는 2개뿐이고 실제 빌드
주체는 Flutter 다. `packages/` 에 JS 패키지가 쌓이고 서로 import 하기 시작하면 재검토할
지점이다 — `apps/*`·`packages/*` 레이아웃이 그대로라 `nx init` 한 번이면 올라탈 수 있다.

### 토큰 파이프라인

소스는 두 묶음으로 나눈다.

- `common.json` — 테마와 무관한 것. 간격, 모서리 반경, 그림자, 모션 지속시간, 폰트 크기·굵기.
- `theme.json` — 색과 컴포넌트 토큰. 지금 앱이 다크 단일 테마이므로 한 벌로 시작하고,
  라이트가 생기면 파일을 분리한다. 생성기는 처음부터 테마별 분기를 전제로 짠다.

계층은 점 표기 경로로 둔다 (`color.surface.base`, `component.button.primary.height`).

컴포넌트 토큰이 이 설계의 요점이다. 버튼 높이·반경·상태 불투명도를 소스에 올려야 Dart 위젯과
웹 컴포넌트가 같은 숫자를 읽는다. 색만 공유하면 색은 같고 모양이 다른 버튼이 나온다.

```
component.button.primary.height         48
component.button.primary.radius         {radius.md}
component.button.primary.bg             {color.brand.gradient}
component.button.primary.pressedOpacity 0.7
```

값에는 다른 토큰을 참조하는 별칭을 허용한다. 반경을 바꿀 때 한 곳만 고친다.

**치수는 375 기준 원시 숫자로 저장한다.** `scale` 곱셈은 소비 지점에서 한다. 토큰에 scale을
녹이면 플랫폼마다 다른 값이 필요해져 단일 출처가 성립하지 않는다.

생성은 범용 토큰 변환 엔진을 쓰되, **Dart 포맷터는 자작한다.** 기성 엔진의 Flutter 지원이
신뢰할 수준이 아니다. 변환 규칙은 다음과 같다.

| 토큰 종류 | Dart 출력 | CSS 출력 |
|---|---|---|
| 색 | `Color(0xAARRGGBB)` | `#RRGGBB` / `rgba()` |
| 치수 | 숫자 (`double`) | `px` 숫자 |
| 폰트 굵기 | `FontWeight.w<n>` | 숫자 |
| 모션 | `Duration(milliseconds: n)` | `ms` |
| 그라데이션 | `LinearGradient(begin·end·colors·stops)` | `linear-gradient(...)` |

그라데이션이 가장 까다롭다. 현재 `AppColors`에 방향이 서로 다른 그라데이션이 여러 개 있고
(좌→우, 상→하), `stops`도 명시돼 있다. 소스에는 **각도와 정지점을 중립 표현으로 저장**하고,
Dart는 `Alignment` 쌍으로, CSS는 `deg`로 각각 변환한다. 좌→우·상→하 같은 축 정렬만
지원하고 임의 각도는 필요해질 때 넓힌다.

### 생성물 일치 검증

CI에서 생성을 재실행하고 작업 트리가 깨끗한지 본다.

```
pnpm tokens:build
git diff --exit-code
```

이것만으로 손으로 고친 생성물이 전부 걸린다. 생성물에 "수정 금지, 소스는
`packages/design-tokens/source/`" 헤더를 넣어 의도를 코드에 남긴다.

여기에 **대비(contrast) 검증**을 더한다. 텍스트 색과 배경 색 쌍을 토큰 기준으로 계산해
기준 미달이면 실패시킨다. 다크 테마에서 회색 계열이 여러 단계 있어 사람 눈으로는 놓친다.

### 브리지 규약

통신을 단계로 쪼개고, 각 단계를 별도 파일로 둔다. 뒤 단계를 추가할 때 앞 단계 파일을
건드리지 않는다.

| 단계 | 방향 | 용도 | 형태 |
|---|---|---|---|
| A | 웹 → 네이티브 | 단방향 통지 | 웹이 메시지 채널로 문자열 전송 |
| B | 네이티브 → 웹 | 브로드캐스트 | 네이티브가 JS 실행, 웹은 커스텀 이벤트 수신 |
| C | 웹 ↔ 네이티브 | 요청·응답 | Promise 기반 호출, 식별자로 응답 짝 맞춤, 에러 전파 |

컨텐츠성 화면은 A와 B로 거의 끝난다 (본문 높이 통지, 로그인 상태 전달, 테마 전달). C는
공유·딥링크·권한처럼 네이티브 기능을 호출할 때 필요해진다. **A부터 넣고 필요할 때 B·C를
더한다.** 처음부터 C를 짜면 쓰지 않는 추상이 남는다.

웹 페이지는 브리지 객체 존재 여부로 **웹뷰 안인지 판별**한다. 일반 브라우저에서는 네이티브
의존 버튼을 비활성화하고 안내를 띄운다. 같은 페이지를 웹에도 노출할 계획이므로 이 분기가
처음부터 필요하다.

### Flutter 쪽 배치

2026-11-10 에 `lib/` 전체가 feature 단위 구조로 바뀌었다
(→ [폴더 구조](../../wiki/architecture/folder-structure.md)). 웹뷰 관련 코드는 그 위에
이렇게 얹는다.

```
apps/mobile/lib/
├── core/
│   └── ui/
│       └── webview/
│           └── warding_webview.dart   웹뷰 컨테이너 **하나**
├── app/
│   ├── bridge/                        ← 신규: 웹 ↔ 네이티브 경계
│   │   ├── bridge_channel.dart        Stage A/B 전송 계층
│   │   └── bridge_contract.dart       웹이 요구하는 Stage 선언
│   └── navigation/
│       └── webview_routes.dart        ← 신규: 웹으로 간 화면 단일 목록
└── features/{기능}/presentation/
    ├── screens/                       Flutter 로 남는 화면
    └── widgets/
```

**웹뷰 컨테이너를 기능별로 복제하지 않는다.** 기능마다 두면 URL 만 다른 거의 같은 파일이
수십 개가 된다. `core/ui/webview/` 에 하나 두고 URL 은
`app/navigation/webview_routes.dart` 에서 주입받는다.

**`bridge/` 를 `app/` 아래 둔다.** 웹뷰가 요청하는 네이티브 기능(공유·딥링크·권한)은
여러 기능의 화면·구현을 알아야 하므로 앱 셸의 성격이다 — `app/` 의 판별 기준("기능 2개
이상의 화면이나 구현을 알아야 하나")에 맞는다. 데이터 요청 핸들러는 없다(위 Decisions
"데이터는 웹이 직접 받는다" 참고).

`app/navigation/webview_routes.dart` 가 **전환 상태의 단일 출처**다. 어느 화면이 웹으로 갔는지
한 파일에서 보이고, 웹 배포 파이프라인의 브리지 계약 가드가 읽어야 하는 데이터가 바로
이것이다(아래 "웹 배포 파이프라인" 참고).

```dart
const webviewRoutes = {
  '/community/post/:id': WebRoute(path: 'community/post', stage: Stage.b),
  '/notice/:id':         WebRoute(path: 'notice',         stage: Stage.a),
};
```

**아직 검증되지 않은 설계다.** 웹뷰 화면을 하나도 만들지 않은 상태에서 그린 것이라,
첫 화면을 옮겨 보고 확정한다 — 컨테이너 하나가 화면별 스크롤·높이 동기화 차이를
파라미터로 흡수할 수 있는지, 그리고 SSR 첫 페인트가 CSR 대비 체감상 빠른지(웹뷰 로드
시작 → 첫 페인트를 Stage A 로 통지받아 측정한다).

### 치수 규약 재현

웹뷰 루트에서 Flutter와 같은 수식을 쓴다.

```css
:root {
  --scale: calc(clamp(320px, 100vw, 430px) / 375);
}
```

토큰 값은 375 기준 원시 숫자이므로, 소비할 때 `calc(<토큰> * var(--scale))`로 쓴다.
Flutter가 `수치 * scale`을 하는 것과 같은 결과가 된다.

### 이음새 처리

- 웹뷰 배경을 네이티브 배경과 **같은 토큰**으로 고정하고, 로드 완료 전까지 네이티브 배경을
  덮어 흰 플래시를 막는다. 다크 테마라 이것이 체감 품질에 가장 크게 영향한다.
- 스크롤 바운스·오버스크롤 글로우·탭 하이라이트를 웹뷰 쪽에서 네이티브 느낌에 맞춘다.
- 폰트는 네이티브가 fallback으로 렌더되는 현 상태를 웹이 따라가게 맞춘다. 양쪽을 동시에
  정리하기 전까지 웹에만 정식 폰트를 넣지 않는다 — 웹뷰만 달라 보이는 것이 더 나쁘다.

### 컴포넌트 범위

구현은 두 벌이지만 전부 두 벌 만들지 않는다.

| 분류 | 처리 |
|---|---|
| 양쪽에 나옴 — 버튼·칩·카드·배지·빈 상태·스켈레톤 | 두 벌 구현(`core/ui/` ↔ 웹), 컴포넌트 토큰으로 계약 고정 |
| 웹뷰에만 — 본문 렌더러·리치텍스트·댓글 | 웹만 |
| 네이티브에만 — 쇼츠 피드·온보딩·하단탭·권한 플로우 | Flutter만 (`features/{기능}/presentation/widgets/`) |

**`core/ui/` 가 "양쪽에 나오는 것" 의 경계다.** 아키텍처 전환으로 앱 전역 공용 위젯이
거기 모였으니(2026-11-17 기준 47 개), 웹에 React 로 만들 대상은 그 안에서 고른다.
기능 전용 위젯 12 개를 각 기능으로 내려 경계가 더 선명해졌고, 지금 `core/ui` 는
`features`·`app` 참조가 0 건이라 웹으로 옮길 때 딸려올 것이 없다. 기능 전용 위젯
(`features/{기능}/presentation/widgets/`)은 애초에 공유 대상이 아니다.

목록을 미리 확정하지 않는다. **첫 전환 화면에서 실제로 필요한 것만** 웹에 만들고, 그것이
"양쪽에 나오는 것" 목록의 초안이 된다.

### 개발 환경

웹 개발 서버와 Flutter를 각각 띄우고, Flutter 쪽에서 플랫폼별로 주소를 분기한다.
iOS 시뮬레이터는 `localhost`, Android 에뮬레이터는 `10.0.2.2`로 가야 한다. 이 분기를
설정 파일 한 곳에 둔다. 릴리즈에서는 배포된 웹 주소를 쓴다.

### 웹 배포 파이프라인 — 기존 패치 워크플로우와의 관계

패치 배포 워크플로우를 웹 배포와 네이티브 배포를 함께 다루는 하나로 만드는 안을 검토했다.
**파일을 합치지 않고, 설계 원칙만 물려받는다.**

합치지 않는 이유는 겉보기와 달리 공유할 코드가 거의 없기 때문이다. 패치 워크플로우의
`verify` 잡은 다섯 스텝인데, 네 개가 패치 고유 개념에 묶여 있다.

| 스텝 | 웹 배포 재사용 |
|---|---|
| 태그 파싱 (`patch/<릴리즈 버전>/<번호>`) | 불가 — "어느 릴리즈 위에 붙는가"가 전제. 웹엔 이 개념이 없다 |
| annotated 태그 확인 | 부분 — 규약으로 쓸 수는 있으나 웹은 태그 트리거가 맞지 않다 |
| pubspec ↔ 패치 대상 버전 일치 | 불가 — 웹 배포는 pubspec 과 무관하다 |
| 네이티브·에셋 변경 차단 | 불가 — 패치가 없어지면 이 가드의 존재 이유도 사라진다 |
| analyze·test | 개념만 — 웹은 다른 도구(린트·웹 테스트)를 쓴다 |

구조적으로도 세 군데가 어긋난다.

- **트리거 모델.** 패치는 태그를 밀어야 돌고, 그것이 "사람이 내보낸다고 명시하는 행위"로
  의도된 설계다. 웹은 심사 없는 즉시 반영이 목적이므로 머지 즉시 배포가 맞다. 배포마다
  annotated 태그를 요구하면 웹으로 옮기는 이점을 스스로 깎는다. 하나의 워크플로우에 조건으로
  섞으면 양쪽이 서로의 가드를 우회하는 틈이 생긴다.
- **동시성 정책.** 패치는 중복 실행을 **기다린다**(`cancel-in-progress: false`) — 패치가 두 개
  쌓이면 설치 수 기준 과금 한도를 두 배 먹기 때문이다. 웹은 최신 커밋만 유효하므로 취소가
  맞다. 이는 워크플로우 레벨 설정이라 잡별로 다르게 줄 수 없다.
- **e2e 전략.** 패치는 통과를 기다린다. 웹은 네이티브 시뮬레이터 e2e 가 필요 없고 웹 쪽
  테스트가 필요하다. `needs` 구성을 공유할 수 없다.

반면 물려받을 **원칙**은 분명하다.

1. **즉시 사용자에게 가는 배포는 검증을 기다린다.** 웹 배포도 심사가 없어 같은 성질이다.
   테스트 통과 전 배포를 막는다.
2. **그 경로로 내보낼 수 없는 변경을 미리 거른다.** 패치의 네이티브·에셋 차단 가드와 같은
   구조로, 웹 버전은 **브리지 계약 위반 차단**이 된다. 웹이 상위 Stage API 를 쓰는데 배포된
   앱의 최소 버전이 그것을 지원하지 않으면 구버전 사용자에게 깨진 화면이 간다. 웹 쪽이
   요구하는 브리지 Stage 와 앱 최소 지원 버전을 비교해 배포를 막는다.
3. **가드를 셸 스크립트로 회귀 테스트한다.** 패치 가드가 `patch-deploy-test.sh` 로 검증되는
   것과 같은 방식이다. 배포 조건은 실제로 배포해 봐야 도는 부분이라 눈으로 검증되지 않는다.
4. **동시성 정책을 의식적으로 정한다.** 값은 반대지만, 정해야 한다는 자각 자체가 자산이다.

따라서 파일 배치는 이렇게 된다.

```
.github/workflows/
  web-deploy.yml          신규 — 머지 트리거, 중복 시 이전 실행 취소
  web-deploy-test.sh      신규 — 브리지 계약 가드 회귀 테스트
  patch-deploy.yml        유지 → Shorebird 제거 시 삭제
  release-deploy.yml      유지 → Shorebird 제거 시 빌드 명령 교체
```

공통 스텝이 실제로 쌓이면 그때 composite action 으로 뽑는다. 지금 추상화하면 공유할 것이
거의 없는 둘을 억지로 묶는 셈이 된다.

Discord 알림 잡도 재사용 후보로 검토했으나, 재사용 가치가 크지 않다. 공유 가능한 것은 결과
아이콘 매핑과 "취소를 실패와 구분한다"는 판단 정도이고, 제목·푸터·잡 목록·출력 변수는 전부
패치 고유다. 웹 배포 알림은 따로 쓰고, 두 번째·세 번째 소비자가 생기면 그때 묶는다.

## Decisions

- **Flutter를 유지한다.** RN 전환은 목적 세 가지를 더 잘 풀지 못하고 재작성 비용만 늘린다.
- **모노레포로 간다.** 단 Flutter 루트를 옮기지 않는 비대칭 배치다. 릴리즈 자동화의 경로
  가정을 건드리지 않는 것이 모노레포의 어떤 정돈보다 우선한다.
- **토큰 단일 출처는 중립 JSON이다.** Dart를 출처로 두면 Dart 전용 표현(`LinearGradient`,
  `Alignment`)이 섞여 CSS 변환이 지저분해진다. 현재 `core/theme/app_colors.dart`가 이미
  그 상태다.
- **생성물을 커밋하고 CI로 일치만 검증한다.** 생성을 빌드 선행 조건으로 만들지 않는다.
- **컴포넌트 토큰까지 소스에 올린다.** 색만 공유하는 것으로는 디자인 시스템이 갈리는 것을
  막지 못한다.
- **치수는 375 기준 원시값으로 저장하고 scale은 소비 지점에서 곱한다.**
- **Dart 포맷터는 자작한다.** 기성 엔진의 Flutter 지원에 의존하지 않는다.
- **웹은 Next.js(App Router) + SSR 이다.** SEO 가 아니라 **첫 페인트 속도**가 목적이다 —
  CSR 이면 웹뷰가 빈 HTML 을 받고 JS 다운·파싱 뒤에야 API 를 부르는데, SSR 은 그 API 호출이
  서버-서버 구간으로 옮겨간다(모바일 네트워크 1회 → 데이터센터 내부 1회). 2026-11-17 확인:
  `community_repository.fetchPostDetail` 이 `_optionalAuthGet` 을 써서 **비회원 조회가 이미
  열려 있다** — 백엔드 선행 작업 없이 Next 서버가 글을 받을 수 있다. 토큰이 있을 때만 붙는
  필드(차단 필터·내 좋아요/스크랩)는 hydrate 뒤 클라이언트에서 채운다.
- **데이터는 웹이 직접 받는다.** `bridge/handlers/`(웹 요청 → Flutter repository)를 만들지
  않는다. 그 경로면 서버가 데이터를 몰라 SSR 로 그릴 게 없고, 응답 필드가 늘 때마다 Flutter
  를 고쳐야 해서 "심사 없이 배포" 라는 목적과 어긋난다. **브리지는 토큰·테마·본문 높이·
  네이티브 기능 호출만** 맡는다(Stage A·B 로 충분).
- **브리지는 Stage A부터 넣는다.** 양방향 호출은 필요해질 때 더한다.
- **토큰을 런타임에 받지 않는다.** 색·수치를 서버에서 받아 `const` 를 포기하는 안을
  검토했으나(`AppColors.` 참조 1299건 / 190파일, 그중 `const` 위젯 42건), **실제로 자주
  바뀌는 것은 레이아웃이고 그건 토큰으로 못 바꾼다.** 색 조정은 드물다. 레이아웃까지
  즉시 배포되는 수단은 웹뷰뿐이라 거기에 투자한다.
- **전환 범위는 컨텐츠성 화면부터.** 인터랙션이 무거운 화면은 네이티브로 남긴다.
- **웹 배포 워크플로우를 패치 워크플로우와 합치지 않는다.** 트리거 모델·동시성 정책·e2e
  전략이 어긋나고 공유할 코드가 거의 없다. 대신 검증 선행·배포 불가 변경 차단·가드의 셸
  회귀 테스트라는 설계 원칙을 물려받는다.

## Out of scope

- ~~Flutter 프로젝트 루트 이동 (`apps/mobile/`)~~ — **2026-11-17에 했다.** 제외 근거였던
  "워크플로우 전면 수정"이 실측 36곳(cwd 변경 13곳)으로 기계적 치환 분량이었고, 태그를
  밀지 않고도 analyze·test·iOS 빌드·셸 회귀로 대부분 검증됐다. 근거와 남은 위험은
  Summary 참고.
- **Shorebird 제거.** 웹뷰 전환이 끝나면 걷어내기로 방향은 정했다(→ [intent.md](./intent.md)
  의 "Shorebird 의 향방"). 배포 파이프라인 변경 범위가 커서 별도 슬러그로 분리한다.

  **2026-11-17 확인: 패치가 이미 실질적으로 쓰이지 않는다.** 과금이 패치 설치 수 기준인데
  (Free 5,000/월) MAU 가 9,000 이라 한 번 내보내면 한도가 찬다. 마지막 패치 태그가
  `patch/1.0.34+84/1`(10-19)이고 그 뒤로 릴리즈만 4번 나갔다. 즉 **지금도 디자인시스템
  변경은 스토어 심사를 거친다** — "전환 기간에는 비상 핫픽스 수단으로 남겨 둔다" 는 앞선
  서술이 실제와 다르다. 네이티브 배포를 줄이는 수단은 웹뷰 전환뿐이고, 그래서 전환 속도가
  이 작업의 실질 가치를 결정한다.
- RN 전환.
- 웹을 독립 제품으로 내는 것. 지금은 "앱 안의 웹"이다.
- Figma Variables 연동. 토큰 소스를 사람이 고치는 것으로 시작한다.
- 폰트 정식 등록 (`Pretendard`·`Open Sans`). 별도 작업으로 뺀다.
- 라이트 테마. 생성기는 테마 분기를 전제로 짜되 지금은 다크 한 벌만 낸다.
- 네이티브 화면의 토큰 치환 일괄 적용. 생성물이 기존 `AppColors` API를 유지하면 호출부는
  그대로 둘 수 있다.
- 기존 목업 `tokens.css` 생성 경로 정리. 현황 확인 후 판단한다.

## Open questions

- 토큰 생성물이 기존 `AppColors` API(클래스명·필드명)를 그대로 유지할 수 있는가. 유지하면
  호출부를 손대지 않아도 되고, 이 작업의 범위가 크게 줄어든다. 그라데이션 필드가 변수다.
- 목업 `tokens.css`의 기존 생성 경로가 실제로 어디에 있는가. warding-docs 쪽 스크립트인지,
  수동인지. 드리프트가 이미 있으면 그 정리가 선행 작업이 된다.
- 토큰 이름에 의미 계층을 한 겹 올릴지. 지금 이름(`narDark800`)은 용도가 코드에 남지 않아
  웹에서 같은 색을 다른 용도로 쓰기 시작하면 갈린다. 다만 전면 개명은 호출부를 전부 건드린다.
  원시 이름을 유지하고 의미 별칭을 추가하는 절충이 가능한지 확인이 필요하다.
- ~~첫 전환 대상 화면~~ → **커뮤니티 글 상세로 정했다.** 최근 3개월 `presentation` 커밋이
  12건으로 잦고, 비회원 조회가 열려 있어 SSR 이 바로 되며, 진입점 6곳이 전부
  `PostDetailScreen(postId)` 한 형태라 치환이 기계적이다. 다음은 공지 3화면(이미 마크다운
  렌더러를 쓴다).
- Next 서버 콜드스타트가 SSR 이득을 얼마나 깎는가. Vercel 서버리스면 첫 요청이 느리다.
  상시 구동으로 올릴지, 아니면 콜드스타트가 체감되지 않는 수준인지 첫 화면에서 측정한다.
- 웹뷰 패키지 선택. 기능·문서 범위가 넓은 쪽과 유지보수가 활발한 쪽의 트레이드오프가 있다.
  Stage A·B만 쓰는 동안은 차이가 작아 보이므로, 유지보수를 우선하고 C 단계에서 재검토하는
  방안이 있다.
- 웹 호스팅·배포 경로. 심사 없는 배포가 목적이므로 배포 파이프라인이 토큰 CI와 어떻게 묶일지.
  웹 배포 워크플로우의 구체 설계는 전환 범위(어느 화면을 먼저 옮기는가)가 정해진 뒤에 한다 —
  브리지 계약 가드가 무엇을 비교해야 하는지가 그 범위에 달려 있다.
- 브리지 계약 가드가 "앱 최소 지원 버전"을 어디서 읽을까. 앱이 스토어에 나간 버전과 웹이
  요구하는 Stage 를 대조해야 하는데, 그 대조 기준을 레포 안의 선언 파일로 둘지 런타임
  협상으로 둘지. 선언 파일이면 사람이 갱신을 빠뜨릴 수 있고, 런타임 협상이면 가드가
  배포 시점에 막지 못한다.
- 그라데이션 변환에서 임의 각도를 지원할 필요가 있는가. 현재는 축 정렬만 쓰인다.
