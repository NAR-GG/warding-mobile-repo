# Spec: 웹뷰 점진 전환 — 모노레포 배치와 토큰 단일 출처

Intent: [intent.md](./intent.md)
warding-docs: 해당 없음 (개발 쪽 구조 작업)

## Summary

Flutter 앱을 유지한 채 컨텐츠성 화면을 웹뷰로 점진 전환한다. 이를 위해 세 가지를 정한다.

1. **토큰 단일 출처** — JSON 소스 하나에서 Dart와 CSS를 생성하고, 생성물 일치를 CI로 검증한다.
2. **브리지 규약** — 웹↔네이티브 통신을 단계(Stage)로 쪼개 누적 호환으로 넓힌다.
3. **레포 배치** — 모노레포로 간다. 단 Flutter 프로젝트 루트는 옮기지 않는다.

3번이 이 Spec의 핵심 결정이다. "모노레포"의 통상적인 형태는 `apps/mobile/`, `apps/web/`으로
나란히 내리는 것인데, 이 레포에서는 그렇게 하지 않는다. 릴리즈·패치 자동화가 레포 루트를
Flutter 루트로 가정하고 있고 그 가정은 태그를 밀어야 검증되기 때문이다. 대신 **Flutter는
루트에 그대로 두고, 웹과 토큰을 하위 디렉터리로 더한다.**

## Requirements

### 기능

- 토큰 소스 JSON에서 `core/theme/app_colors.dart`(또는 후속 토큰 파일)와 웹용 CSS를 생성한다.
- 생성은 결정적이다. 같은 소스에서 항상 같은 바이트가 나온다.
- 생성물이 소스와 어긋나면 CI가 실패한다.
- 토큰에 색·간격·모서리·그림자·모션·컴포넌트 토큰을 담는다.
- 웹뷰 페이지가 `scale` 수식을 CSS로 재현해 네이티브와 같은 치수로 렌더된다.
- 웹 페이지가 웹뷰 안인지 일반 브라우저인지 감지하고, 브라우저에서는 네이티브 의존 기능을
  비활성화한다.
- 웹↔네이티브 통신이 단방향 → 브로드캐스트 → 양방향 호출 순으로 확장되며, 뒤 단계가 앞
  단계를 깨지 않는다.

### 비기능

- 릴리즈·패치 워크플로우의 경로 가정을 변경하지 않는다.
- 웹 디렉터리 추가가 Flutter 빌드·analyze·test에 영향을 주지 않는다.
- 토큰 생성이 Flutter 빌드의 선행 조건이 되지 않는다 (생성물을 커밋하므로).
- 네이티브↔웹뷰 이음새에서 배경 플래시가 보이지 않는다.

## Design / Approach

### 레포 배치

```
warding-mobile-repo/            ← Flutter 루트 (그대로)
  pubspec.yaml
  lib/
    core/theme/
      app_colors.dart           ← 생성물 (커밋됨, 수정 금지 헤더)
  design_tokens/                ← 신규: 토큰 단일 출처
    source/
      common.json               간격·모서리·그림자·모션·타이포
      theme.json                색·컴포넌트 토큰
    build/
      tokens.css                웹 소비용
    config.mjs                  생성 설정 + 커스텀 Dart 포맷터
    package.json
  web/                          ← 신규: 웹뷰용 웹 앱
    ...
  pnpm-workspace.yaml           ← 신규: design_tokens + web + tools/discord-bridge
```

Flutter가 루트에 있고 Node 워크스페이스가 하위에 얹히는 **비대칭 모노레포**다. 통상적인
모양은 아니지만, 이 레포에서는 이 비대칭이 비용을 가장 낮춘다.

- 릴리즈·패치 워크플로우, Shorebird 설정, e2e, 태그 규약이 손대지 않은 상태로 유지된다.
- `tools/discord-bridge/`에 이미 Node 프로젝트가 있어, 워크스페이스로 묶을 대상이 하나 더
  늘어나는 것에 가깝다.
- 토큰 PR 하나로 Dart 생성물과 CSS 생성물이 같이 바뀌므로, 드리프트가 구조적으로 막힌다.
  이것이 모노레포에서 실제로 얻는 이득이다.

웹을 별도 레포로 두는 안도 검토했다. 토큰만 패키지로 공유하면 되지만, 그러면 토큰 변경이
두 레포에 걸친 PR 두 개가 되고 버전 어긋남이 생긴다. 지금 막으려는 문제가 그것이므로
같은 레포를 택한다.

`web/`은 뒤에 `apps/web/`으로 옮겨도 Flutter 쪽에 영향이 없다. 반대 방향(Flutter를 내리는 것)
만 비싸다. 즉 이 배치는 나중에 통상적인 모노레포로 가는 길을 막지 않는다.

### 토큰 파이프라인

소스는 두 묶음으로 나눈다.

- `common.json` — 테마와 무관한 것. 간격, 모서리 반경, 그림자, 모션 지속시간, 폰트 크기·굵기.
- `theme.json` — 색과 컴포넌트 토큰. 지금 앱이 다크 단일 테마이므로 한 벌로 시작하고,
  라이트가 생기면 파일을 분리한다. 생성기는 처음부터 테마별 분기를 전제로 짠다.

계층은 점 표기 경로로 둔다 (`color.surface.base`, `component.button.primary.height`).

컴포넌트 토큰이 이 설계의 요점이다. 버튼 높이·반경·상태 불투명도를 소스에 올려야 Dart 위젯과
웹 컴포넌트가 같은 숫자를 읽는다. 색만 공유하면 색은 같고 모양이 다른 버튼이 나온다.

```
component.button.primary.height         48
component.button.primary.radius         {radius.md}
component.button.primary.bg             {color.brand.gradient}
component.button.primary.pressedOpacity 0.7
```

값에는 다른 토큰을 참조하는 별칭을 허용한다. 반경을 바꿀 때 한 곳만 고친다.

**치수는 375 기준 원시 숫자로 저장한다.** `scale` 곱셈은 소비 지점에서 한다. 토큰에 scale을
녹이면 플랫폼마다 다른 값이 필요해져 단일 출처가 성립하지 않는다.

생성은 범용 토큰 변환 엔진을 쓰되, **Dart 포맷터는 자작한다.** 기성 엔진의 Flutter 지원이
신뢰할 수준이 아니다. 변환 규칙은 다음과 같다.

| 토큰 종류 | Dart 출력 | CSS 출력 |
|---|---|---|
| 색 | `Color(0xAARRGGBB)` | `#RRGGBB` / `rgba()` |
| 치수 | 숫자 (`double`) | `px` 숫자 |
| 폰트 굵기 | `FontWeight.w<n>` | 숫자 |
| 모션 | `Duration(milliseconds: n)` | `ms` |
| 그라데이션 | `LinearGradient(begin·end·colors·stops)` | `linear-gradient(...)` |

그라데이션이 가장 까다롭다. 현재 `AppColors`에 방향이 서로 다른 그라데이션이 여러 개 있고
(좌→우, 상→하), `stops`도 명시돼 있다. 소스에는 **각도와 정지점을 중립 표현으로 저장**하고,
Dart는 `Alignment` 쌍으로, CSS는 `deg`로 각각 변환한다. 좌→우·상→하 같은 축 정렬만
지원하고 임의 각도는 필요해질 때 넓힌다.

### 생성물 일치 검증

CI에서 생성을 재실행하고 작업 트리가 깨끗한지 본다.

```
pnpm --filter design_tokens tokens
git diff --exit-code
```

이것만으로 손으로 고친 생성물이 전부 걸린다. 생성물에 "수정 금지, 소스는
`design_tokens/source/`" 헤더를 넣어 의도를 코드에 남긴다.

여기에 **대비(contrast) 검증**을 더한다. 텍스트 색과 배경 색 쌍을 토큰 기준으로 계산해
기준 미달이면 실패시킨다. 다크 테마에서 회색 계열이 여러 단계 있어 사람 눈으로는 놓친다.

### 브리지 규약

통신을 단계로 쪼개고, 각 단계를 별도 파일로 둔다. 뒤 단계를 추가할 때 앞 단계 파일을
건드리지 않는다.

| 단계 | 방향 | 용도 | 형태 |
|---|---|---|---|
| A | 웹 → 네이티브 | 단방향 통지 | 웹이 메시지 채널로 문자열 전송 |
| B | 네이티브 → 웹 | 브로드캐스트 | 네이티브가 JS 실행, 웹은 커스텀 이벤트 수신 |
| C | 웹 ↔ 네이티브 | 요청·응답 | Promise 기반 호출, 식별자로 응답 짝 맞춤, 에러 전파 |

컨텐츠성 화면은 A와 B로 거의 끝난다 (본문 높이 통지, 로그인 상태 전달, 테마 전달). C는
공유·딥링크·권한처럼 네이티브 기능을 호출할 때 필요해진다. **A부터 넣고 필요할 때 B·C를
더한다.** 처음부터 C를 짜면 쓰지 않는 추상이 남는다.

웹 페이지는 브리지 객체 존재 여부로 **웹뷰 안인지 판별**한다. 일반 브라우저에서는 네이티브
의존 버튼을 비활성화하고 안내를 띄운다. 같은 페이지를 웹에도 노출할 계획이므로 이 분기가
처음부터 필요하다.

### Flutter 쪽 배치

2026-11-10 에 `lib/` 전체가 feature 단위 구조로 바뀌었다
(→ [폴더 구조](../../wiki/architecture/folder-structure.md)). 웹뷰 관련 코드는 그 위에
이렇게 얹는다.

```
lib/
├── core/
│   └── ui/
│       └── webview/
│           └── warding_webview.dart   웹뷰 컨테이너 **하나**
├── bridge/                            ← 신규: 웹 ↔ 네이티브 경계
│   ├── bridge_channel.dart            Stage A/B/C 전송 계층
│   ├── bridge_contract.dart           웹이 요구하는 Stage 선언
│   └── handlers/                      웹 요청 → repository 호출
├── routing/
│   └── webview_routes.dart            ← 신규: 웹으로 간 화면 단일 목록
└── features/{기능}/presentation/
    ├── screens/                       Flutter 로 남는 화면
    └── widgets/
```

**웹뷰 컨테이너를 기능별로 복제하지 않는다.** 기능마다 두면 URL 과 브리지 핸들러만 다른
거의 같은 파일이 27 개가 된다. `core/ui/webview/` 에 하나 두고 URL 은
`routing/webview_routes.dart` 에서, 핸들러는 `bridge/` 에서 주입받는다.

**`bridge/` 를 `features/` 밖에 둔다.** 웹의 데이터 요청을 받아 repository 를 호출하는
코드는 ViewModel 도 repository 도 아닌 **경계(boundary)** 다. 의존 방향은 `bridge/ → core/`
와 `bridge/ → features/{기능}/domain/` 이고, `presentation/` 을 import 하지 않는다.

`routing/webview_routes.dart` 가 **전환 상태의 단일 출처**다. 어느 화면이 웹으로 갔는지
한 파일에서 보이고, 웹 배포 파이프라인의 브리지 계약 가드가 읽어야 하는 데이터가 바로
이것이다(아래 "웹 배포 파이프라인" 참고).

```dart
const webviewRoutes = {
  '/community/post/:id': WebRoute(path: 'community/post', stage: Stage.b),
  '/notice/:id':         WebRoute(path: 'notice',         stage: Stage.a),
};
```

**아직 검증되지 않은 설계다.** 웹뷰 화면을 하나도 만들지 않은 상태에서 그린 것이라,
두 가지는 첫 화면을 옮겨 보고 확정한다 — `bridge/handlers/` 가 Stage A·B 만 쓰는 동안
정말 필요한지, 그리고 컨테이너 하나가 화면별 스크롤·높이 동기화 차이를 파라미터로
흡수할 수 있는지.

### 치수 규약 재현

웹뷰 루트에서 Flutter와 같은 수식을 쓴다.

```css
:root {
  --scale: calc(clamp(320px, 100vw, 430px) / 375);
}
```

토큰 값은 375 기준 원시 숫자이므로, 소비할 때 `calc(<토큰> * var(--scale))`로 쓴다.
Flutter가 `수치 * scale`을 하는 것과 같은 결과가 된다.

### 이음새 처리

- 웹뷰 배경을 네이티브 배경과 **같은 토큰**으로 고정하고, 로드 완료 전까지 네이티브 배경을
  덮어 흰 플래시를 막는다. 다크 테마라 이것이 체감 품질에 가장 크게 영향한다.
- 스크롤 바운스·오버스크롤 글로우·탭 하이라이트를 웹뷰 쪽에서 네이티브 느낌에 맞춘다.
- 폰트는 네이티브가 fallback으로 렌더되는 현 상태를 웹이 따라가게 맞춘다. 양쪽을 동시에
  정리하기 전까지 웹에만 정식 폰트를 넣지 않는다 — 웹뷰만 달라 보이는 것이 더 나쁘다.

### 컴포넌트 범위

구현은 두 벌이지만 전부 두 벌 만들지 않는다.

| 분류 | 처리 |
|---|---|
| 양쪽에 나옴 — 버튼·칩·카드·배지·빈 상태·스켈레톤 | 두 벌 구현(`core/ui/` ↔ 웹), 컴포넌트 토큰으로 계약 고정 |
| 웹뷰에만 — 본문 렌더러·리치텍스트·댓글 | 웹만 |
| 네이티브에만 — 쇼츠 피드·온보딩·하단탭·권한 플로우 | Flutter만 (`features/{기능}/presentation/widgets/`) |

**`core/ui/` 가 "양쪽에 나오는 것" 의 경계다.** 아키텍처 전환으로 앱 전역 공용 위젯이
거기 모였으니(59 개), 웹에 React 로 만들 대상은 그 안에서 고른다. 기능 전용 위젯
(`features/{기능}/presentation/widgets/`)은 애초에 공유 대상이 아니다.

목록을 미리 확정하지 않는다. **첫 전환 화면에서 실제로 필요한 것만** 웹에 만들고, 그것이
"양쪽에 나오는 것" 목록의 초안이 된다.

### 개발 환경

웹 개발 서버와 Flutter를 각각 띄우고, Flutter 쪽에서 플랫폼별로 주소를 분기한다.
iOS 시뮬레이터는 `localhost`, Android 에뮬레이터는 `10.0.2.2`로 가야 한다. 이 분기를
설정 파일 한 곳에 둔다. 릴리즈에서는 배포된 웹 주소를 쓴다.

### 웹 배포 파이프라인 — 기존 패치 워크플로우와의 관계

패치 배포 워크플로우를 웹 배포와 네이티브 배포를 함께 다루는 하나로 만드는 안을 검토했다.
**파일을 합치지 않고, 설계 원칙만 물려받는다.**

합치지 않는 이유는 겉보기와 달리 공유할 코드가 거의 없기 때문이다. 패치 워크플로우의
`verify` 잡은 다섯 스텝인데, 네 개가 패치 고유 개념에 묶여 있다.

| 스텝 | 웹 배포 재사용 |
|---|---|
| 태그 파싱 (`patch/<릴리즈 버전>/<번호>`) | 불가 — "어느 릴리즈 위에 붙는가"가 전제. 웹엔 이 개념이 없다 |
| annotated 태그 확인 | 부분 — 규약으로 쓸 수는 있으나 웹은 태그 트리거가 맞지 않다 |
| pubspec ↔ 패치 대상 버전 일치 | 불가 — 웹 배포는 pubspec 과 무관하다 |
| 네이티브·에셋 변경 차단 | 불가 — 패치가 없어지면 이 가드의 존재 이유도 사라진다 |
| analyze·test | 개념만 — 웹은 다른 도구(린트·웹 테스트)를 쓴다 |

구조적으로도 세 군데가 어긋난다.

- **트리거 모델.** 패치는 태그를 밀어야 돌고, 그것이 "사람이 내보낸다고 명시하는 행위"로
  의도된 설계다. 웹은 심사 없는 즉시 반영이 목적이므로 머지 즉시 배포가 맞다. 배포마다
  annotated 태그를 요구하면 웹으로 옮기는 이점을 스스로 깎는다. 하나의 워크플로우에 조건으로
  섞으면 양쪽이 서로의 가드를 우회하는 틈이 생긴다.
- **동시성 정책.** 패치는 중복 실행을 **기다린다**(`cancel-in-progress: false`) — 패치가 두 개
  쌓이면 설치 수 기준 과금 한도를 두 배 먹기 때문이다. 웹은 최신 커밋만 유효하므로 취소가
  맞다. 이는 워크플로우 레벨 설정이라 잡별로 다르게 줄 수 없다.
- **e2e 전략.** 패치는 통과를 기다린다. 웹은 네이티브 시뮬레이터 e2e 가 필요 없고 웹 쪽
  테스트가 필요하다. `needs` 구성을 공유할 수 없다.

반면 물려받을 **원칙**은 분명하다.

1. **즉시 사용자에게 가는 배포는 검증을 기다린다.** 웹 배포도 심사가 없어 같은 성질이다.
   테스트 통과 전 배포를 막는다.
2. **그 경로로 내보낼 수 없는 변경을 미리 거른다.** 패치의 네이티브·에셋 차단 가드와 같은
   구조로, 웹 버전은 **브리지 계약 위반 차단**이 된다. 웹이 상위 Stage API 를 쓰는데 배포된
   앱의 최소 버전이 그것을 지원하지 않으면 구버전 사용자에게 깨진 화면이 간다. 웹 쪽이
   요구하는 브리지 Stage 와 앱 최소 지원 버전을 비교해 배포를 막는다.
3. **가드를 셸 스크립트로 회귀 테스트한다.** 패치 가드가 `patch-deploy-test.sh` 로 검증되는
   것과 같은 방식이다. 배포 조건은 실제로 배포해 봐야 도는 부분이라 눈으로 검증되지 않는다.
4. **동시성 정책을 의식적으로 정한다.** 값은 반대지만, 정해야 한다는 자각 자체가 자산이다.

따라서 파일 배치는 이렇게 된다.

```
.github/workflows/
  web-deploy.yml          신규 — 머지 트리거, 중복 시 이전 실행 취소
  web-deploy-test.sh      신규 — 브리지 계약 가드 회귀 테스트
  patch-deploy.yml        유지 → Shorebird 제거 시 삭제
  release-deploy.yml      유지 → Shorebird 제거 시 빌드 명령 교체
```

공통 스텝이 실제로 쌓이면 그때 composite action 으로 뽑는다. 지금 추상화하면 공유할 것이
거의 없는 둘을 억지로 묶는 셈이 된다.

Discord 알림 잡도 재사용 후보로 검토했으나, 재사용 가치가 크지 않다. 공유 가능한 것은 결과
아이콘 매핑과 "취소를 실패와 구분한다"는 판단 정도이고, 제목·푸터·잡 목록·출력 변수는 전부
패치 고유다. 웹 배포 알림은 따로 쓰고, 두 번째·세 번째 소비자가 생기면 그때 묶는다.

## Decisions

- **Flutter를 유지한다.** RN 전환은 목적 세 가지를 더 잘 풀지 못하고 재작성 비용만 늘린다.
- **모노레포로 간다.** 단 Flutter 루트를 옮기지 않는 비대칭 배치다. 릴리즈 자동화의 경로
  가정을 건드리지 않는 것이 모노레포의 어떤 정돈보다 우선한다.
- **토큰 단일 출처는 중립 JSON이다.** Dart를 출처로 두면 Dart 전용 표현(`LinearGradient`,
  `Alignment`)이 섞여 CSS 변환이 지저분해진다. 현재 `core/theme/app_colors.dart`가 이미
  그 상태다.
- **생성물을 커밋하고 CI로 일치만 검증한다.** 생성을 빌드 선행 조건으로 만들지 않는다.
- **컴포넌트 토큰까지 소스에 올린다.** 색만 공유하는 것으로는 디자인 시스템이 갈리는 것을
  막지 못한다.
- **치수는 375 기준 원시값으로 저장하고 scale은 소비 지점에서 곱한다.**
- **Dart 포맷터는 자작한다.** 기성 엔진의 Flutter 지원에 의존하지 않는다.
- **브리지는 Stage A부터 넣는다.** 양방향 호출은 필요해질 때 더한다.
- **전환 범위는 컨텐츠성 화면부터.** 인터랙션이 무거운 화면은 네이티브로 남긴다.
- **웹 배포 워크플로우를 패치 워크플로우와 합치지 않는다.** 트리거 모델·동시성 정책·e2e
  전략이 어긋나고 공유할 코드가 거의 없다. 대신 검증 선행·배포 불가 변경 차단·가드의 셸
  회귀 테스트라는 설계 원칙을 물려받는다.

## Out of scope

- Flutter 프로젝트 루트 이동 (`apps/mobile/`). 릴리즈·패치 워크플로우 전면 수정이 따라오고
  태그를 밀어야 검증되므로, 필요해지면 별도 작업으로 분리한다.
- **Shorebird 제거.** 웹뷰 전환이 끝나면 걷어내기로 방향은 정했으나(→ [intent.md](./intent.md)
  의 "Shorebird 의 향방"), 전환 기간에는 비상 핫픽스 수단으로 남겨 둔다. 배포 파이프라인
  변경 범위가 커서 별도 슬러그로 분리한다.
- RN 전환.
- 웹을 독립 제품으로 내는 것. 지금은 "앱 안의 웹"이다.
- Figma Variables 연동. 토큰 소스를 사람이 고치는 것으로 시작한다.
- 폰트 정식 등록 (`Pretendard`·`Open Sans`). 별도 작업으로 뺀다.
- 라이트 테마. 생성기는 테마 분기를 전제로 짜되 지금은 다크 한 벌만 낸다.
- 네이티브 화면의 토큰 치환 일괄 적용. 생성물이 기존 `AppColors` API를 유지하면 호출부는
  그대로 둘 수 있다.
- 기존 목업 `tokens.css` 생성 경로 정리. 현황 확인 후 판단한다.

## Open questions

- 토큰 생성물이 기존 `AppColors` API(클래스명·필드명)를 그대로 유지할 수 있는가. 유지하면
  호출부를 손대지 않아도 되고, 이 작업의 범위가 크게 줄어든다. 그라데이션 필드가 변수다.
- 목업 `tokens.css`의 기존 생성 경로가 실제로 어디에 있는가. warding-docs 쪽 스크립트인지,
  수동인지. 드리프트가 이미 있으면 그 정리가 선행 작업이 된다.
- 토큰 이름에 의미 계층을 한 겹 올릴지. 지금 이름(`narDark800`)은 용도가 코드에 남지 않아
  웹에서 같은 색을 다른 용도로 쓰기 시작하면 갈린다. 다만 전면 개명은 호출부를 전부 건드린다.
  원시 이름을 유지하고 의미 별칭을 추가하는 절충이 가능한지 확인이 필요하다.
- 첫 전환 대상 화면. 커뮤니티 글 본문이 후보다 (현재 외부 브라우저로 띄우고 있어 체감 개선이
  명확하고, 네이티브 기능 의존이 적다). 공지·뉴스도 후보.
- 웹뷰 패키지 선택. 기능·문서 범위가 넓은 쪽과 유지보수가 활발한 쪽의 트레이드오프가 있다.
  Stage A·B만 쓰는 동안은 차이가 작아 보이므로, 유지보수를 우선하고 C 단계에서 재검토하는
  방안이 있다.
- 웹 호스팅·배포 경로. 심사 없는 배포가 목적이므로 배포 파이프라인이 토큰 CI와 어떻게 묶일지.
  웹 배포 워크플로우의 구체 설계는 전환 범위(어느 화면을 먼저 옮기는가)가 정해진 뒤에 한다 —
  브리지 계약 가드가 무엇을 비교해야 하는지가 그 범위에 달려 있다.
- 브리지 계약 가드가 "앱 최소 지원 버전"을 어디서 읽을까. 앱이 스토어에 나간 버전과 웹이
  요구하는 Stage 를 대조해야 하는데, 그 대조 기준을 레포 안의 선언 파일로 둘지 런타임
  협상으로 둘지. 선언 파일이면 사람이 갱신을 빠뜨릴 수 있고, 런타임 협상이면 가드가
  배포 시점에 막지 못한다.
- 그라데이션 변환에서 임의 각도를 지원할 필요가 있는가. 현재는 축 정렬만 쓰인다.
