# Intent: 웹뷰 점진 전환과 디자인 시스템 단일 출처

## Problem

컨텐츠성 화면(커뮤니티 글 본문·공지·뉴스 등)을 웹으로 옮겨 스토어 심사 없이 배포하고, 같은
화면을 웹과 앱에서 함께 쓰고 싶다. 그런데 웹 화면을 새로 만들기 시작하면 디자인 시스템이
두 벌로 갈린다.

지금 색 토큰의 단일 출처는 `lib/styles/app_colors.dart` 하나다. 웹이 생기면 CSS 쪽에
같은 색을 다시 적게 되고, 손으로 맞추는 동기화는 반드시 깨진다. 이미 그 징후가 있다 —
`CLAUDE.md`는 목업의 `assets/tokens.css`가 `app_colors.dart`에서 자동 생성된다고
적어 뒀지만, 이 레포에 그 생성 스크립트가 없다. 문서가 앞서갔거나 생성기가 다른 곳에 있다.

갈리는 건 색만이 아니다. 더 깨지기 쉬운 쪽은 **토큰에 적히지 않은 값들**이다. 버튼 높이,
모서리 반경, 눌림 상태 불투명도 같은 것은 지금 각 위젯 안에 흩어져 있어서, 웹에서 같은
버튼을 만들 때 참조할 출처가 없다. 색이 같아도 모양이 다른 버튼이 나온다.

치수 규약도 어긋날 소지가 있다. 이 레포의 UI 규칙은 "시안 기준 폭 375, 화면 폭을
320~430으로 clamp 한 뒤 375로 나눈 `scale`을 수치에 곱한다"다. 웹이 이 수식을 쓰지 않으면
같은 토큰을 써도 크기가 다르게 렌더된다. 네이티브 헤더 아래 웹뷰 본문이 붙는 화면에서
바로 드러난다.

한편 전환 방식 자체도 결정이 필요하다. React Native로 갈아타고 디자인 시스템을 공유하는
선택지를 검토했으나, 목적 세 가지(심사 없는 배포·웹과 앱의 화면 공유·컨텐츠성 화면) 중
어느 것도 RN이 더 잘 풀어주지 않는다고 판단했다. 심사 없는 배포는 Shorebird 파이프라인으로
이미 돌아가고 있고, 웹과의 실제 공유 범위는 RN이어도 토큰·API 레이어에 머문다. 업계 사례도
RN 기반 앱이 자주 바뀌는 컨텐츠 화면은 웹뷰로 분리하는 쪽이다. 즉 RN을 택해도 웹뷰 레이어와
토큰 단일 출처 작업은 그대로 남고, 전면 재작성 비용만 추가된다.

## Proposed outcome

Flutter 앱을 유지한 채 컨텐츠성 화면부터 웹뷰로 점진 전환한다. 그 전제로 디자인 토큰의
단일 출처를 코드 바깥의 중립 포맷으로 올리고, Flutter용·웹용 산출물을 거기서 생성한다.
컴포넌트 구현은 두 벌이지만, 두 벌이 참조하는 수치는 한 벌이다.

- 토큰 소스를 JSON으로 두고 Dart·CSS 산출물을 생성한다. 생성물이 소스와 어긋나면 CI가 깨진다.
- 색뿐 아니라 간격·모서리·그림자·모션·**컴포넌트 토큰**(버튼 높이·반경·상태 불투명도 등)까지
  소스에 올려, 양쪽 구현이 같은 수치를 읽게 한다.
- 웹뷰 쪽이 `scale` 수식을 CSS로 동일하게 재현해, 같은 토큰이 같은 크기로 렌더되게 한다.
- 웹↔네이티브 통신 규약을 단계적으로 정의해, 전환 범위를 넓힐 때 앞 단계를 깨지 않는다.
- 레포 배치(모노레포 여부)를 정한다. 단, 릴리즈 자동화를 깨뜨리지 않는 선에서.

도착점은 **Shorebird 를 걷어낸 상태**다. 코드푸시가 메우던 자리를 웹 배포가 대신하기
때문이다 — 웹뷰로 간 화면은 서버 배포로 즉시 반영되고, 네이티브에 남는 수정은 스토어 심사를
감수한다. 두 벌의 즉시 배포 경로를 유지할 이유가 없다. 순서는 "웹뷰 범위를 넓힌다 →
네이티브에 남은 화면이 충분히 줄어든다 → Shorebird 를 제거한다"이고, 마지막 단계는 배포
파이프라인 변경 범위가 커서 **별도 슬러그로 분리한다**(아래 Constraints·Open questions).

## Affected users and systems

- **사용자**: 네이티브와 웹뷰가 섞인 화면을 보게 된다. 이음새의 배경색·폰트·치수 차이가
  그대로 체감 품질이 된다. 현재 앱이 다크 테마라 흰 플래시가 특히 눈에 띈다.
- **`lib/styles/app_colors.dart`**: 손으로 쓰는 파일에서 생성물로 성격이 바뀐다. 현재 279줄,
  대부분 단색이고 `LinearGradient`가 여러 개 섞여 있다. 그라데이션은 Dart 전용 표현
  (`begin`/`end`/`stops`)을 써서 중립 포맷으로 옮길 때 별도 설계가 필요하다.
- **릴리즈·패치 자동화**: `release/<pubspec version>` 태그 규약, 네이티브 변경 차단 가드,
  e2e 워크플로우가 모두 레포 루트를 Flutter 프로젝트 루트로 가정한다. 폴더를 내리면 전부
  손봐야 하고, 이 부류는 **태그를 밀어야 검증된다**. 리스크가 비대칭이다.
- **warding-docs**: 목업 `assets/tokens.css`의 생성 방향이 바뀐다 (Dart에서 뽑는 것이 아니라
  공통 소스에서 뽑는다).
- **`wiki/`**: 아키텍처·디자인 개념 문서에 웹 레이어가 추가된다.
- **웹뷰 패키지**: 이 레포에 자체 웹뷰 화면은 아직 없다. `webview_flutter`가
  `pubspec.lock`에만 있는 전이 의존성이고(유튜브 임베드 경유), `pubspec.yaml`에 직접 선언이
  없다. 커뮤니티 본문 렌더러는 인앱 웹뷰를 의존성·성능 이유로 보류하고 외부 브라우저를 띄운다.
  즉 첫 웹뷰 화면을 새로 도입하는 상황이고 패키지 선택이 열려 있다.

## Constraints

- **Flutter를 유지한다.** RN 전환은 위 판단으로 범위에서 제외한다.
- **릴리즈·패치 파이프라인을 깨뜨리지 않는다.** 토큰 작업과 레포 재배치를 같은 변경에 섞지
  않는다. 실패 지점이 겹치면 원인 분리가 안 된다.
- **Shorebird 를 전환 도중에 걷어내지 않는다.** 전환이 진행되는 동안에는 네이티브 비중이
  여전히 크고, 그 기간의 비상 핫픽스 수단을 없애면 전환 자체가 위험해진다. 제거 시점의 영향
  범위는 비교적 좁다 — Dart 코드에 Shorebird SDK 의존이 없다(`shorebird_code_push` 를 쓰지
  않고, 코드의 Shorebird 언급은 모두 "이 변경은 패치로 못 나간다"를 설명하는 주석이다).
  걷어낼 것은 배포 파이프라인과 문서, 그리고 asset 으로 등록된 설정 파일이다.
- **생성물은 커밋한다.** `app_colors.dart`가 사라지면 Flutter 빌드·analyze가 생성 단계에
  의존하게 되고, 전환 기간의 Shorebird 패치 가드도 영향을 받는다. 커밋한 뒤 CI로 일치만
  검증한다. 이 제약은 Shorebird 제거 후에도 유지한다 — 생성 단계를 빌드 선행 조건으로
  만들지 않는 것 자체가 목적이다.
- **생성은 결정적이어야 한다.** 같은 소스에서 항상 같은 산출물이 나와야 일치 검증이 성립한다.
- **치수 규약은 375 기준 원시값으로 저장한다.** `scale` 곱셈은 각 플랫폼 소비 지점에서 한다.
  토큰에 scale을 미리 녹이면 안 된다.
- **전환 범위는 컨텐츠성 화면으로 시작한다.** 인터랙션이 무거운 화면(쇼츠 세로 피드·온보딩·
  하단탭·권한 플로우)은 네이티브로 남긴다. 웹뷰로 품질이 나오지 않는다.
- 폰트는 현재 `Pretendard`·`Open Sans`가 pubspec에 미등록이라 네이티브가 fallback으로
  렌더된다. 웹에만 제대로 넣으면 웹뷰만 폰트가 달라 보인다.

## Open questions

- 웹 코드를 어디에 둘까. 이 레포를 모노레포로 만들 것인지, 별도 레포로 두고 토큰만 공유할
  것인지. 릴리즈 자동화의 루트 경로 가정이 모노레포 비용의 대부분이다.
- 토큰 소스의 소유자는 누구인가. Figma Variables에서 내려올 것인지, 레포의 JSON을 사람이
  고치는 것인지. 후자면 디자인 변경이 코드 PR로만 들어온다.
- 목업 `tokens.css`의 기존 생성 경로가 실제로 어디에 있는가. warding-docs 쪽에 스크립트가
  있는지, 수동인지. 이미 드리프트가 있다면 그 정리가 출발점이다.
- `app_colors.dart`의 그라데이션(방향·stops 포함)을 중립 포맷에서 어떻게 표현할까.
  CSS `linear-gradient`와 Dart `LinearGradient`가 각도·정렬 표현이 달라 변환 규칙이 필요하다.
- 토큰 이름을 원시(`narDark800`) 그대로 둘지, 의미 계층(`surface.elevated` 등)을 한 겹
  올릴지. 지금 이름은 용도가 코드에 남지 않아, 웹에서 같은 색을 다른 용도로 쓰기 시작하면
  갈린다.
- 폰트 정리를 이 작업에 포함할지, 별도로 뺄지.
- 첫 전환 대상 화면을 무엇으로 할지.
- Shorebird 를 걷어낼 시점을 무엇으로 판단할까. "웹뷰 전환 완료"의 기준이 필요하다. 전환된
  화면 수인지, 최근 핫픽스 중 네이티브에 걸린 비율인지. 후자가 더 직접적인 신호로 보인다 —
  일정 기간 패치가 전부 웹 배포로 해결됐다면 Shorebird 는 이미 쓰이지 않는 것이다.
- 웹뷰 패키지 선택. 기능·문서 범위가 넓은 쪽과 유지보수가 활발한 쪽의 트레이드오프가 있다.
