# Spec: 웹뷰 이관 (줄기 문서)

상태: **검토 중.** 이관 착수 여부는 아직 정하지 않았다. 착수 조건은 [Open questions](#open-questions)에 있다.
warding-docs: 해당 없음 (화면 기획이 아니라 개발 쪽 구조 변경이다)

이 문서는 웹뷰 이관의 **줄기**다. 결정·원칙·가지 지도·상태만 둔다. 세부 설계는 가지 문서에
한 번만 쓰고, 여기에는 한 줄 요약과 링크만 남긴다. 운영 규칙은 [문서 운영 규칙](#문서-운영-규칙)에 있다.

## Summary

스토어 정규 릴리즈가 나갈 때마다 사용자가 업데이트 팝업을 보고 스토어에 가야 했다. 이를 줄이기 위해
Flutter 앱을 껍데기로 남기고 하단 5개 탭 안의 화면을 웹으로 옮기는 안을 검토했다.

2026-11-07 기준으로 상황이 바뀌었다.

- 최근 스토어 릴리즈 9번(1.0.34 ~ 1.0.42) 중 네이티브·에셋을 바꾼 것은 1.0.40(티어 이미지 11장) 하나다.
  나머지 8번은 Dart만 바뀌어서 Shorebird 패치로 낼 수 있었다.
- 최소 버전 태그(`[:mav:]`)가 붙은 릴리즈만 팝업을 띄우게 바뀌었다(#428).
- Shorebird 패치가 태그 자동 배포로 돌고 있다(`patch-deploy.yml`).
- Shorebird Pro는 월 $20에 패치 설치 5만 건이다. MAU 9천 명이 월 4번 패치를 받아도 그 안에 들어간다.

그래서 **지금 당장 이관할 근거는 약하다.** 대신 이관하든 안 하든 가치가 있는 가지(e2e 기준선,
라우트 게이트웨이)를 먼저 진행하고, 이관 본체는 착수 조건이 충족될 때 시작한다.

웹뷰만 줄 수 있는 이득은 다음 네 가지다. 이관 여부는 이 중 무엇이 필요해지는지로 판단한다.

1. 앱 재시작 없이 즉시 반영된다 (Shorebird 패치는 재시작 2번이 필요하다).
2. 에셋을 자유롭게 추가할 수 있다 (1.0.40 같은 경우).
3. 브라우저 접속, 링크 공유 미리보기, 검색 노출이 생긴다.
4. 화면 단위로 비율 공개·즉시 롤백을 할 수 있다.

## Requirements

1. 지금 되는 기능은 하나도 깨지지 않아야 한다. 판정 기준은 [e2e 기준선](../e2e-baseline/spec.md)이다.
2. 모든 단계는 스토어 배포 없이 되돌릴 수 있어야 한다.
3. 스토어 업데이트는 최소 1번, 현실적으로 2번 안에 끝나야 한다.
4. 분석(Mixpanel) 대시보드와 이벤트 정의가 바뀌지 않아야 한다.
5. 이관 중에 디자인을 새로 만들지 않는다 (원칙 3).

## Design / Approach

### 원칙

1. **교살자 무화과 패턴으로 옮긴다.** 모든 화면 진입을 라우트 게이트웨이 한 곳으로 모으고, 그 뒤에서
   화면을 하나씩 Flutter판에서 웹판으로 바꾼다. 한 번에 다 바꾸지 않는다.
2. **특성화 테스트를 먼저 만든다.** 지금 앱의 동작을 블랙박스 e2e로 고정한 뒤 옮긴다. 기준선이 없으면
   "똑같이 된다"를 증명할 수 없다.
3. **이식과 개선을 섞지 않는다.** 이식 중에는 화면을 픽셀 단위로 똑같이 옮기고, 디자인·기능 변경은
   스위치를 100% 켠 뒤에 한다. 디자이너가 공통 컴포넌트나 토큰을 다시 설계할 필요가 없다. 목업이 이미
   HTML이고 `tokens.css`가 `app_colors.dart`에서 자동 생성되기 때문이다.
4. **모든 이음새에 계약을 둔다.** API는 `docs/openapi_spec.json`, 브리지는 버전이 붙은 메시지 스키마,
   분석은 `analytics_events.dart`의 이벤트 카탈로그를 계약으로 쓴다. 계약은 양쪽 테스트가 같은 파일을 읽는다.
5. **모든 단계는 되돌릴 수 있다.** 화면 스위치, 자동 대체(웹 실패 시 Flutter판), Flutter 코드 보존.
6. **껍데기가 먼저 나간다.** 스토어 설치가 퍼지는 데 1~2주가 걸리므로, 웹 화면보다 먼저 전부 꺼진 상태로 낸다.
7. **운영 지표로 판정한다.** 단계별 공개마다 Flutter 쪽과 웹 쪽 지표를 비교하고, 기준을 넘으면 내린다.

### 구조

```
┌──────────── 스토어 앱 (Flutter 껍데기) ────────────┐
│ 네이티브로 남는 것                                  │
│   스플래시 · 하단 탭바 · 소셜 로그인 · 푸시 · 홈 위젯    │
│   라이브 액티비티 · 권한 · 사진 선택 · 공유 · 업데이트   │
│                                                    │
│ 라우트 게이트웨이  openRoute('/match/123?tab=live')   │
│   └ 화면 스위치 설정을 보고 Flutter 화면 or WebView     │
│                                                    │
│ WebView 호스트 + 브리지 (JS ↔ Dart)                  │
└────────────────────────┬───────────────────────────┘
                         │
┌────────────────────────▼───────────────────────────┐
│ 웹앱: 배포하면 바로 반영, 심사 없음                     │
└────────────────────────────────────────────────────┘
```

분석 이벤트는 웹이 Mixpanel을 직접 부르지 않는다. 브리지로 `track(name, props)`를 넘기고 Flutter
`Analytics`가 보낸다. 그래야 distinct_id·앱 버전·OS 속성이 그대로이고 MEU가 두 배로 잡히지 않는다.
단 지금 `page_view`는 `AnalyticsRouteObserver`가 자동으로 찍으므로, 웹 안의 화면 이동은 웹이 직접 보내야 한다.

### 가지 지도

| 가지 (슬러그) | 내용 | 이관 안 해도 가치가 있나 | 상태 |
|---|---|---|---|
| [e2e-baseline](../e2e-baseline/spec.md) | 구현을 모르는 블랙박스 e2e, 목 서버, 동등성 판정 | **있다.** Shorebird 패치는 심사 없이 바로 나가므로 게이트가 필요하다 | 설계 중 |
| route-gateway | `openRoute` 하나로 진입 통일 (`Navigator.push` 73곳, 푸시 탭, 위젯, 딥링크), 푸시 페이로드 `route` 필드 | **있다.** 새 알림 종류와 딥링크를 스토어 업데이트 없이 처리한다 | 미작성 |
| webview-shell | WebView 호스트, 화면 스위치 설정, 자동 대체, 프리워밍 | 없다 | 미작성 |
| webview-bridge | 브리지 프로토콜 v1, 버전 협상, 토큰 전달, 분석 중계 | 없다 | 미작성 |
| web-app | 웹 스택, 토큰·컴포넌트 이식, 호스팅, 배포 게이트 | 없다 | 미작성 |

진행 순서는 e2e-baseline → route-gateway → (착수 결정) → webview-shell·webview-bridge·web-app 병행이다.

### 아직 가지가 없는 세부 (가지가 생기면 그쪽으로 옮긴다)

**네이티브에 남는 것.** FCM 푸시 수신·탭 처리, 알림 권한, 홈 위젯(`WardingScheduleWidget`), 라이브
액티비티, 소셜 로그인 4종, 하단 탭바(유리 효과 포함), 스플래시·업데이트 체크.

**브리지가 필요한 것.** 토큰 전달·갱신, 로그아웃·탈퇴, 알림 권한 요청, 사진 선택(Android WebView는
`<input type=file>`이 기본으로 안 된다), 공유·외부 링크·햅틱, **홈 위젯 갱신**(지금 `ScheduleViewModel`이
부르므로 일정 탭을 옮기면 위젯이 조용히 멈춘다), 라이브 액티비티 시작·종료, 로컬 저장값 읽기·쓰기, 분석 중계.

**사용자가 끊김을 느낄 수 있는 지점.** 로그인 토큰 전달, 로컬 저장값, 진입 경로 누락, 첫 로딩 흰 화면,
네트워크 실패, 웹 배포 중 버전 섞임, 브리지 버전 불일치, iOS 입력창 확대·노치·롱프레스, 폰트 차이
(앱은 Pretendard 미등록으로 대체 폰트를 쓴다).

### 스토어 업데이트 횟수

| 순서 | 언제 | 무엇 | 필수 |
|---|---|---|---|
| ① | 착수 1주차 | 껍데기 v1: 게이트웨이, 화면 스위치(기본값 전부 flutter), WebView 호스트, 자동 대체, 브리지 v1 | 필수 |
| ② | 첫 파일럿 10% 이후 | 껍데기 v2: 파일럿에서 드러난 브리지 누락 보완 | 현실적으로 필요 |
| ③ | 전 탭 100% + 4주 안정 | Flutter 화면 코드 삭제 | 선택 |

route-gateway를 이관 전에 먼저 스토어로 내 두면 ①의 범위가 줄어든다.

### 단계별 공개

팀 내부 100% → 1% → 10% → 50% → 100%. 단계마다 화면 오류율, 진입 후 행동 전환율, 체류 시간,
크래시를 Flutter 쪽과 비교한다. 화면 이관 순서는 커뮤니티 → 일정·경기 목록 → 홈·경기 상세·마이다.
커뮤니티는 네이티브 의존이 사진 첨부 하나뿐이고 실패해도 경기 정보에 영향이 없다.

## Decisions

- 껍데기는 Flutter를 유지한다. 로그인·푸시·위젯·라이브 액티비티가 이미 Flutter에서 돈다.
- 웹이 Mixpanel을 직접 부르지 않고 브리지로 중계한다.
- 이식 중 디자인·기능 변경은 하지 않는다.
- 이관 본체보다 e2e-baseline과 route-gateway를 먼저 한다.
- 이 문서가 2026-11-01 초안(`~/Downloads/와딩_웹앱이관_계획.md`)을 대체한다.

## Out of scope

- Shorebird 대체: 이관해도 Dart 셸 수정은 Shorebird 패치로 낸다.
- 하단 탭바·로그인·푸시의 웹 이전.
- React Native, Flutter Web, Capacitor 전환.

      필요해진다, Shorebird 비용이 월 $N을 넘는다. 팀과 수치로 합의한다.

## 문서 운영 규칙

- 줄기(이 문서)에는 결정, 원칙, 가지 지도, 상태만 둔다. 세부는 가지에 **한 번만** 쓰고, 줄기는 한 줄 요약과 링크로 가리킨다.
- 가지는 별도 슬러그 폴더다. 레포 규칙상 한 폴더에 spec은 1개이기 때문이다(`intent/loop-engineering-workflow/spec.md` 저장 구조).
- 가지는 **작업을 시작할 때** 만든다. 빈 가지 파일을 미리 만들지 않는다. 그 전까지 세부는 위 "아직 가지가 없는 세부"에 둔다.
- 가지 spec 맨 위에는 `줄기: [webview-migration](../webview-migration/spec.md)`를 적는다.
- 가지가 다시 커지면 같은 규칙으로 슬러그를 더 쪼갠다.
- 가지 상태가 바뀌면 줄기의 가지 지도도 같은 PR에서 갱신한다.
- 구현 직전 계획은 각 가지 폴더의 `plan.md`에 쓴다.
